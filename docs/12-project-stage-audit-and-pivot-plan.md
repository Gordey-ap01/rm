# Аудит этапа и план поворота после reschedule-среза

Дата: 2026-07-14

Назначение: зафиксировать, что проект не потерял состояние между сессиями, но локально зациклился на безопасных доработках одного блока. Этот документ не заменяет `current-state`, `07`, `09`, `10` и `11`; он задает следующий фокус, чтобы новые сессии не продолжали микросрезы вокруг планов переноса без явной причины.

## Источники проверки

- `git log` по ветке `codex/domain-appointments-v2`;
- `docs/current-state.md`;
- `docs/project-recovery-manifest.md`;
- `docs/next-chat-prompt.md`;
- `docs/07-updated-domain-model-after-interview.md`;
- `docs/08-parallel-agent-execution-plan.md`;
- `docs/09-cascade-reschedule-domain-slice.md`;
- `docs/10-reschedule-chain-dependencies-contract.md`;
- `docs/11-plan-terminal-status-contract.md`;
- `graphify-out/graph.json` как навигационный индекс, не как источник правды.

## Диагноз

Связь между сессиями не потеряна полностью: в репозитории есть последовательная история коммитов, recovery-манифест, переносимый промпт, журнал состояния и актуальные контракты. Но после 2026-07-12 работа локально ушла в повторяющийся режим: почти все свежие срезы усиливали уже созданный слой persisted-планов переноса, цепочек, ссылок, архивного текста, work queue и dashboard-сигналов.

Эти изменения не были бесполезными: они закрывали реальные UX/control gaps и проходили тесты. Но дальнейшее продолжение в том же стиле несет риск тратить время на вторичную полировку одного модуля вместо движения к интервью-driven продукту.

## Что считать закрытым для текущей фазы

- Stage 5 табличной UX/UI стабилизации закрыт.
- Базовая нормализация групповых занятий уже есть: участники, назначения специалистов, кабинетные лимиты, представители, participant-level списания.
- Persisted-планы переноса реализованы: план, шаги, согласования, статусы согласований, staff absence plan, ручной разбор конфликтов, одноразовое кабинетное разрешение при применении шага.
- Атомарные цепочки переноса реализованы на текущем уровне: schema, построение цепочки, revalidation, atomic apply, dependency links, registry/work queue/dashboard attention.
- Терминальные статусы планов переноса стабилизированы: terminal action locks, queue filtering, registry/history copy, detail/history copy.

## Stop rule

Больше не брать "еще один non-DB operations UX/control slice" вокруг `/reschedule-plans/`, цепочек, архивных подписей, hash anchors, registry/work queue/dashboard сигналов, если нет одного из условий:

- найден баг, регрессия, ошибка безопасности или потеря данных;
- есть конкретное требование пользователя к этому экрану;
- новый срез входит в утвержденный контракт по расписанию/финансам/статусам.

Отдельный dashboard руководителя именно по цепочкам переноса остается отложенным до реальной управленческой потребности. Текущих registry metrics, dashboard/work queue attention и detail diagnostics достаточно для следующей продуктовой фазы.

## Следующий фокус

Следующий шаг должен быть не микрополировка reschedule-слоя, а новый доменный контракт и первый вертикальный срез из общей модели после интервью.

Приоритетный кандидат: `schedule-capacity-v2` - проверка и UX расписания по кабинетам, групповым занятиям, нескольким специалистам, вместимости и выходу специалиста вне графика.

Причины:

- это ближе всего к повседневной боли администратора;
- это фундамент для корректной записи групп и индивидуальных занятий;
- без надежной вместимости кабинета, назначений специалистов и доступности нельзя безопасно двигать гранты, payroll и импорт;
- часть модели уже есть, поэтому следующий срез может быть вертикальным, а не переписыванием.

## Предлагаемый контракт следующего среза

Рабочее имя: `docs/13-schedule-capacity-v2-contract.md`.

Минимальный scope:

1. Инвентаризация текущей реализации `Room`, `Appointment`, `AppointmentParticipant`, `AppointmentStaffAssignment`, `AppointmentRoomOverride`, `StaffAvailability`, `operations/services/scheduling.py`, форм занятия и calendar API.
2. Формализация инвариантов:
   - индивидуальное занятие блокирует специалиста на пересекающееся время;
   - групповое занятие разрешает несколько получателей только до лимита занятия/кабинета;
   - кабинет может ограничивать одного или нескольких специалистов одновременно;
   - кабинет может ограничивать одного или нескольких получателей одновременно;
   - override кабинета и override графика специалиста требуют явного действия администратора и причины;
   - старые legacy-поля используются только как fallback, если snapshot-строк нет.
3. Gap analysis между `docs/07-updated-domain-model-after-interview.md` и текущим кодом.
4. Решение, нужны ли миграции. Если нужны, один агент становится владельцем `operations/models.py` и migration chain.
5. Вертикальный кодовый срез: БД/валидация/UI/тесты, без изменения ledger/payroll/grant accounting.

Acceptance criteria контракта:

- перечислены все модели и сервисы, которые можно трогать;
- перечислены модели и сервисы, которые нельзя трогать в этом срезе;
- описана стратегия legacy fallback и backfill risk;
- есть тестовые сценарии для индивидуальных, групповых, multi-staff и room override случаев;
- явно указано, можно ли подключать параллельных агентов.

## Параллельные агенты

До утверждения `13-schedule-capacity-v2-contract.md` работать должен один ведущий агент.

Разрешено параллельно только:

- read-only reviewer по текущей модели расписания;
- UX-аналитик без правки кода, если нужно нарисовать сценарий администратора;
- documentation/backup агент без правки моделей, миграций и сервисов.

Запрещено параллельно:

- менять `operations/models.py`;
- создавать миграции;
- менять `operations/services/scheduling.py` и формы занятия двумя агентами одновременно;
- менять ledger/payroll/grant списания в том же срезе.

## Следующий рабочий порядок

1. Обновить recovery-документы, чтобы остановить reschedule-loop.
2. Создать `docs/13-schedule-capacity-v2-contract.md`.
3. Провести read-only аудит текущего кода расписания против `docs/07-updated-domain-model-after-interview.md`.
4. Только после контракта начинать первый вертикальный кодовый срез.
5. После каждого среза обновлять `current-state`, `project-recovery-manifest`, `next-chat-prompt` и Graphify code index.
