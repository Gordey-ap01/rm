# Контракт среза: сквозная приемка операционного и управленческого контуров

Дата: 2026-07-25

Статус: implemented

## Основание

`docs/01-prd.md`, `docs/48-time-off-decision-authority-contract.md`,
`docs/51-payroll-director-approval-contract.md` и
`docs/52-payroll-payout-lifecycle-contract.md` определяют отдельные доменные
срезы. Перед production-preflight необходимо доказать, что их основные факты
сохраняются при прохождении цельных рабочих сценариев, а не только в
изолированных unit-тестах.

## Граница среза

Входит:

1. Сквозной операционный путь: администратор создаёт индивидуальное занятие,
   специалист отмечает проведение, администратор списывает занятие со счёта
   получателя и подготавливает табель.
2. Сквозной путь руководителя: утвердить табель, передать его в выплату и
   зафиксировать один полный факт выплаты.
3. Проверка границы полномочий: администратор не может утвердить, передать или
   выплатить табель; списание получателя и выплата специалисту остаются разными
   финансовыми фактами даже при работе руководителя в операционном контуре.
4. Сквозной путь по отсутствию специалиста: решение администратора по отпуску
   действует оперативно и блокирует запись, остаётся в очереди руководителя;
   решение руководителя переопределяет его, а администратор не может
   переопределить руководителя.

Не входит:

- новая модель, миграция, изменение бухгалтерского учёта или грантовых квот;
- частичные выплаты, сторно payroll и банковская интеграция;
- полное browser-E2E покрытие всех экранов: экранные smoke-проверки остаются
  отдельным слоем после изменения UI;
- импорт Excel, backup/restore и мониторинг.

## Сценарий A: занятие до выплаты

1. Администратор создаёт индивидуальное занятие через `create_appointment` с
   валидируемым расписанием.
2. Специалист отмечает проведение через `record_attendance`; participant/staff
   snapshots сохраняют факт для табеля.
3. Администратор применяет `charge` к подходящему `BalanceAccount`.
4. В ledger появляется ровно один активный debit; остаток счёта уменьшается
   один раз.
5. По этому финансовому факту `generate_accruals_for_staff` создаёт одно
   черновое начисление согласно `StaffCompensationRule`.
6. Администратор формирует черновик `PayrollSheet`; руководитель последовательно
   выполняет `draft -> approved -> sent -> paid`.
7. В конце существуют один debit, одно оплачиваемое начисление, один лист,
   одна выплата и два lifecycle-события (`sent`, `paid`). Сумма выплаты точно
   равна табелю; отдельные `Payment` получателя и `CenterExpense` не создаются.

## Сценарий B: отпуск и приоритет руководителя

1. Специалист создаёт многодневный отпуск, для которого требуется приоритет
   руководителя.
2. Администратор вручную согласует запрос с основанием. Запрос становится
   оперативно действующим, но current decision помечен как ожидающий контроля
   руководителя и остаётся в `attention_queryset`.
3. Новая запись этого специалиста в период отпуска отклоняется schedule
   validation.
4. Руководитель отклоняет или подтверждает решение. Его запись становится
   единственным current decision; предыдущая остаётся в истории через
   `supersedes`.
5. Администратор получает `PermissionDenied` при попытке изменить итоговое
   решение руководителя.

## Инварианты приемки

| Область | Неизменяемый факт |
| --- | --- |
| Расписание | Индивидуальное занятие не создаётся вне доступности специалиста, включая действующий отпуск. |
| Списание | Повторный путь не создаёт второй debit для занятия. |
| Payroll | Начисление возникает только из факта списания и не меняется после утверждения. |
| Выплата | Выплата ровно одна, полная и не смешана с балансом получателя. |
| Полномочия | Финансовые переходы payroll доступны только руководителю. |
| Приоритет | Решение администратора по приоритетной заявке действует сразу, но последнее слово остаётся за руководителем. |
| История | Решения и lifecycle-события сохраняют автора и не уничтожаются при переопределении. |

## Реализация и проверки

- Тесты располагаются в `operations/tests/test_operational_acceptance.py` и
  используют только публичные service write-paths.
- Минимальная проверка: focused pytest на новом модуле, `django check`,
  `makemigrations --check --dry-run` и `ruff check operations rehab_center`.
- Обязательная регрессия: полный pytest на SQLite. PostgreSQL прогоняется для
  существующих конкурентных контрактов; данный срез не добавляет новую схему
  или новую конкурентную точку записи.
- Если сквозной тест обнаружит дефект, сначала фиксируется нарушенный
  инвариант. Исправление допускается только в уже существующем публичном
  сервисе и сопровождается регрессией; расширение требований оформляется
  отдельным контрактом.

## Параллельная работа

DB owner не меняет `operations/models.py` и migration chain в этом срезе.
После фиксации контракта тестовый агент мог бы владеть только новым test module,
а UI агент — только browser smoke и артефактами QA. В текущем проходе это
выполняет один ведущий агент, чтобы быстрее локализовать межконтурный дефект.

## Открытое продолжение

После приемки этого среза следующими остаются production preflight
(backup/restore, monitoring, SMTP, branch protection) и отдельные контракты
persisted transfer/conversion, грантовых квот и управленческих отчётов.
