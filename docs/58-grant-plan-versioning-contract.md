# Контракт версионирования грантового плана

Дата: 2026-07-26

Статус: утвержденный контракт следующего опасного вертикального среза.

## 1. Цель и границы

Руководитель изменяет грантовый план без потери предыдущих значений. Для
каждой квоты услуги и каждого распределения специалисту система показывает
кто, когда и на каком основании создал, изменил или закрыл позицию.

В срез входят:

1. append-only редакции `FundingServiceQuota` и
   `FundingStaffAllocation`;
2. запрет физического удаления и редактирования в обход доменного сервиса;
3. director-only write-path и read-only история для администратора;
4. безопасный legacy backfill без вымышленных решений;
5. связь созданного payroll-начисления с редакцией грантовой ставки;
6. PostgreSQL-сериализация конкурентных редакций и контроля суммы квоты;
7. UI истории и focused browser-приемка.

Не входят:

- изменение `GrantRecipientAllocation` и пополнение счета через ledger;
- фиксированная зарплата за грантовый проект и общий payroll-бюджет;
- снимок закрытого/сданного донорского отчета;
- policy пересечений между разными услугами или источниками;
- квота на категорию услуг без конкретной `Service`.

## 2. Подтвержденные правила

- Квоту и распределение назначает руководитель.
- Администратор готовит расписание и исходные данные, но не утверждает
  грантовый план.
- Квота задается на услугу, затем распределяется между специалистами.
- Быстрый вариант `специалист + количество занятий` остается допустимым без
  ссылки на квоту услуги.
- Смена специалиста не перезаписывает старого: старая позиция закрывается,
  новая создается с собственным периодом.
- Закрытая или архивная история остается доступной для отчета и проверки.
- Интерактивное действие без автора-руководителя и содержательного основания
  недопустимо.

Это исключительная управленческая область из карты полномочий PRD. Правило
ручного решения ожидающего запроса администратором здесь не применяется:
в текущем срезе нет запроса адресату, а происходит утверждение финансового
плана.

## 3. Gap analysis

| Область | Сейчас | После среза |
| --- | --- | --- |
| Редактирование | `ModelForm` меняет строку на месте | Доменный сервис создает новую редакцию |
| Удаление | Возможен физический `DELETE` | Только закрытие с причиной |
| Автор решения | Только generic auditlog | Типизированные `actor`, роль и основание |
| Связь квота-специалист | FK на изменяемую строку | FK на устойчивый корень квоты |
| Лимит квоты | Проверка формы, уязвимая к race | Повторная проверка в транзакции под lock |
| Payroll | Сохраняет ставку и сумму | Дополнительно хранит редакцию-источник |
| Старые строки | Нет доменной версии | Редакция `legacy_import`, автор неизвестен |
| Django admin | Позволяет обход профильного UI | История и корни только для чтения |

## 4. Доменная модель

### `FundingServiceQuota`

Остается устойчивым корнем и текущей проекцией:

- идентичность: `funding_source`, `service`;
- текущие значения: `planned_sessions`, `starts_on`, `ends_on`, `note`;
- `lifecycle_status`: `active`, `closed`;
- `current_revision`: защищенная ссылка на единственную текущую редакцию.

Идентичность после создания не меняется. FK на источник и услугу переводятся
с `CASCADE` на `PROTECT`.

### `FundingServiceQuotaRevision`

- `service_quota`;
- `revision_number`;
- `event_type`: `created`, `revised`, `closed`, `legacy_import`;
- снимок `planned_sessions`, `starts_on`, `ends_on`, `note`,
  `lifecycle_status`;
- `actor`, nullable только для `legacy_import`, `on_delete=PROTECT`;
- `actor_role_snapshot`: `director`, `legacy`;
- `reason`;
- `supersedes`;
- nullable `decided_at`: пусто только для `legacy_import`;
- техническое `created_at`.

### `FundingStaffAllocation`

Остается устойчивым корнем и текущей проекцией:

- неизменяемая идентичность: nullable `service_quota`, `funding_source`,
  `service`, `staff_member`;
- текущие значения: `allocated_sessions`, `session_pay_amount`, `starts_on`,
  `ends_on`, `note`;
- `lifecycle_status`: `active`, `closed`;
- `current_revision`: защищенная ссылка на единственную текущую редакцию.

FK корня переводятся на `PROTECT`. Смена специалиста или привязки к квоте
создает новый корень.

### `FundingStaffAllocationRevision`

- `staff_allocation`;
- `revision_number`;
- `event_type`;
- снимок `allocated_sessions`, `session_pay_amount`, `starts_on`, `ends_on`,
  `note`, `lifecycle_status`;
- `actor`, `actor_role_snapshot`, `reason`;
- `supersedes`, nullable `decided_at`, техническое `created_at`.

### `PayrollAccrual`

Получает nullable FK `grant_allocation_revision`. Для общей ставки и старых
начислений поле пустое. Существующие snapshot-поля ставки, длительности и суммы
остаются источником утвержденной суммы payroll.

## 5. Инварианты

1. Корень указывает ровно на одну свою терминальную `current_revision`;
   nullable разрешен только как техническое окно создания/backfill и считается
   нарушением integrity-check.
2. `(root, revision_number)` уникален; номер строго возрастает.
3. `supersedes` принадлежит тому же корню и не может иметь двух прямых
   преемников.
4. Интерактивная редакция требует `actor`, роль `director` и непустое
   основание.
5. Legacy-редакция не получает вымышленного пользователя или дату решения.
6. Проекция корня после commit совпадает с его текущей редакцией.
7. Редакция после создания не меняет бизнес-поля и не удаляется.
   PostgreSQL-trigger блокирует также обход через `QuerySet.update/delete`.
8. Закрытие не обнуляет историческое количество. Для высвобождения части
   квоты руководитель сначала создает редакцию с новым количеством и
   основанием.
9. Сумма текущих распределений, связанных с квотой, не превышает ее план.
10. Уменьшение квоты ниже уже распределенного количества блокируется.
11. Закрытие квоты блокируется, пока связанная позиция специалиста остается
    активной.
12. Архивный `FundingSource` запрещает новые редакции.
13. Закрытое распределение продолжает давать историческую ставку для даты
    занятия внутри сохраненного периода. Новый будущий период требует новой
    позиции.
14. Утвержденное или выплаченное `PayrollAccrual` не пересчитывается после
    новой редакции. Черновик пересчитывается только пока не включен ни в один
    незакрытый расчетный лист.
15. Для `(источник, услуга, специалист, дата)` допустима не более чем одна
    позиция со ставкой. При legacy-неоднозначности payroll останавливается.
16. Новая редакция получает `expected_revision_id`; устаревшая форма не может
    молча перезаписать более новое решение.
17. Количество и период нельзя изменить так, чтобы освободить уже списанный
    ledger-backed факт.
18. Перед утверждением расчетного листа сумма каждой строки обязана совпадать
    с текущим snapshot начисления.

## 6. Транзакционный write-path

Операции `create`, `revise` и `close` выполняет один сервис
`operations.services.grant_plans`.

Для редакции сервис:

1. проверяет роль руководителя и активность источника;
2. берет `SELECT ... FOR UPDATE` на корень;
3. для распределения блокирует связанную квоту и ее распределения в порядке
   `pk`;
4. сверяет `expected_revision_id`, даты, пересечения, сумму квоты и уже
   списанный факт;
5. добавляет полностью неизменяемую новую редакцию;
6. атомарно обновляет текущую проекцию и `current_revision`;
7. прежнюю редакцию не изменяет;
8. фиксирует все одной транзакцией.

`ModelForm.save(instance=...)`, Django admin и физический `delete()` не
используются как write-path. UI преобразует прежние команды
`Редактировать/Удалить` в `Создать редакцию/Закрыть`.

## 7. UX и роли

На грантовом отчете:

- руководитель видит `Создать редакцию`, `История`, `Закрыть`;
- администратор видит те же значения и историю без управляющих команд;
- закрытая позиция имеет явный статус и остается в подходящем историческом
  периоде;
- форма редакции показывает неизменяемые источник, услугу, специалиста и
  предыдущие значения;
- основание обязательно и не прячется в общем примечании;
- история идет от новой редакции к старой и показывает номер, действие,
  значения, автора, время и основание.

Прямой управляющий HTTP-запрос администратора или специалиста получает `403`.
Попытка изменить архивный источник отклоняется независимо от роли.

## 8. Безопасная миграция

### 58-A. Additive schema

- создать обе таблицы редакций;
- добавить `lifecycle_status` корням;
- добавить nullable `current_revision` обоим корням;
- добавить nullable FK в `PayrollAccrual`;
- не удалять и не переименовывать существующие поля;
- изменить исторически значимые FK на `PROTECT`.

### 58-B. Legacy backfill

- для каждого существующего корня создать редакцию №1 `legacy_import`;
- перенести фактические значения без нормализации и домысливания;
- оставить `actor=NULL`, роль `legacy`;
- оставить `decided_at=NULL`, используя `created_at` только как время загрузки;
- заполнить `current_revision` созданной редакцией;
- сформировать отчет preflight о превышенных квотах и пересечениях, но не
  исправлять их автоматически.

### 58-C. Switch write-path

- подключить доменный сервис, формы редакции/закрытия и read-only admin;
- переключить report/payroll на текущие проекции и revision provenance;
- добавить integrity check проекция ↔ текущая редакция, пересечения квот и
  согласованность строк payroll;
- на время production cutover запретить грантовые записи, выполнить backfill,
  финальный catch-up и только затем включить новый write-path.

### 58-D. Tighten and accept

- добавить constraints после успешного backfill;
- установить PostgreSQL-trigger неизменяемости revision-таблиц;
- проверить миграцию на копии PostgreSQL;
- выполнить focused tests, полный regression и browser smoke;
- обновить только строку `Гранты и зарплата` readiness matrix.

`RunPython` backfill намеренно необратим. Откат приложения не должен запускать
`migrate 0047` и удалять новые таблицы. После появления интерактивных редакций
rollback выполняется отдельным совместимым релизом, сохраняющим историю и
запрещающим прежний незаверсионированный write-path.

## 9. Опасные места

- `CASCADE -> PROTECT` может обнаружить прежние сценарии физического удаления;
- параллельные распределения без row lock могут вместе превысить квоту;
- прямой Django admin или `QuerySet.update()` способен обойти сервис;
- legacy-данные могут уже нарушать будущие правила;
- ставка без revision FK не объясняет источник расчета;
- две legacy-позиции со ставкой на одну дату делают payroll неоднозначным;
- изменение чернового начисления внутри расчетного листа рассинхронизирует
  сумму строки;
- закрытие позиции без корректной даты способно оставить ставку применимой к
  будущему занятию.

Эти риски закрываются запретом admin-write, model guards, транзакционным
сервисом, preflight-командой и PostgreSQL concurrency tests.

## 10. Acceptance criteria

- создание директором дает корень и редакцию №1 с автором и основанием;
- изменение сохраняет прежние значения и создает редакцию №2;
- изменение бизнес-идентичности блокируется;
- закрытие не удаляет корень или историю;
- администратор читает историю, не видит команд и получает `403` на write URL;
- специалист получает `403`;
- legacy backfill не создает вымышленного автора;
- из двух команд с одним `expected_revision_id` проходит одна; вторая получает
  конфликт, не создавая новую редакцию;
- два конкурентных распределения не превышают план квоты;
- уменьшение плана ниже распределенного количества отклоняется;
- уменьшение или сдвиг периода ниже уже списанного факта отклоняется;
- payroll-начисление по грантовой ставке ссылается на выбранную редакцию и
  сохраняет snapshot суммы;
- неоднозначная грантовая ставка останавливает payroll;
- начисление внутри активного листа не переоценивается, а несовпадение строки
  и начисления блокирует утверждение;
- архивный источник остается read-only;
- integrity check на принятой БД не находит расхождений проекции и редакции;
- PostgreSQL migration/preflight, focused tests, Ruff, Django check, полный
  regression и desktop/mobile browser smoke проходят.

## 11. Владение и параллельная работа

До фиксации этого контракта работает один ведущий агент. После фиксации:

- один DB owner единолично меняет `operations/models.py`, миграции,
  `grant_plans.py` и DB-тесты;
- UI-поток можно выделить только после появления стабильного API сервиса и не
  давать ему модели/миграции;
- независимый агент выполняет read-only review схемы и конкурентных
  инвариантов;
- итоговую интеграцию, migration chain и приемку выполняет ведущий агент.
