```text
Продолжаем проект "Радость моя" в репозитории D:\РадостьМояАвтоматизация\RMcodex.

Важно: сейчас задача НЕ "срочный MVP". Цель - серьезный рабочий продукт для реабилитационного центра: удобный администратору, понятный руководителю, надежный по расписанию, финансам, программам занятий и табелям.

Сначала обязательно прочитай:

Контекст:
- Текущий стек: Django 5, templates, Bootstrap, FullCalendar, PostgreSQL, Redis, Docker Compose, Caddy.
- Production временно доступен через https://rm.147-45-102-93.sslip.io/.
- React можно рассматривать только точечно для сложного календаря/планировщика, но не начинать переписывание без доказанной необходимости.
- После нового интервью ожидаются серьезные изменения в требованиях, БД, UX/UI и бизнес-логике.

Твоя задача сначала не кодить, а сделать серьезный аналитический проход:

1. Инвентаризируй новые требования из интервью.
2. Сверь их с текущим PRD и текущей системой.
3. Составь gap analysis: что уже есть, что частично есть, чего нет, где текущая модель неправильна.
4. Отдельно проверь критические зоны:
   - расписание по специалистам и кабинетам;
   - несколько специалистов в одном кабинете и ограничение вместимости кабинета;
   - рабочее время, отпуска, отгулы, выход специалиста вне графика;
   - программы занятий, каскады, блоки, серии и нумерация;
   - счета баланса в занятиях и рублях;
   - гранты, фонды, спонсоры, личные оплаты;
   - бронь неоплаченных занятий;
   - миграция средств между каскадами и автоматический пересчет количества занятий;
   - отмена день-в-день и предложения, как сдвинуть расписание без свободных окон;
   - согласование со специалистом, представителем или получателем;
   - табель специалиста и отчеты руководителя;
   - мобильный кабинет специалиста;
   - импорт Excel после стабилизации модели.
5. Зафиксируй противоречия и вопросы к пользователю. Не задавай сразу 30 вопросов: сгруппируй их по блокам и выдели самые критичные.
6. Предложи обновленный PRD или список точечных правок к PRD.
7. Предложи доменную модель: какие сущности нужны, какие текущие сущности надо изменить, какие миграции потенциально опасны.
8. Предложи UX/UI карту основных сценариев администратора и руководителя.
9. Составь пошаговый план реализации вертикальными срезами с acceptance criteria и проверками.
10. Реши, где нужен один агент, а где можно подключить несколько агентов.

Критическое правило по агентам:
- Сначала один ведущий агент делает анализ, PRD, доменную модель и план.
- Несколько агентов подключать только после согласования контрактов.
- Один агент должен быть владельцем миграций БД.
- Нельзя давать нескольким агентам одновременно менять operations/models.py и migration chain.

Критическое правило по коду:
- Не начинай править код до плана, если изменения затрагивают БД, финансы, расписание или статусы.
- После утверждения плана делать небольшие вертикальные срезы: БД + валидация + UI + тесты.
- Не коммитить секреты, пароли, реальные персональные данные и production-конфиги.
- Не трогать неотносящиеся пользовательские файлы.

Ожидаемый первый результат:
1. Краткий диагноз текущего состояния.
2. Список найденных пробелов после интервью.
3. Список критичных уточняющих вопросов.
4. Предлагаемый план работ по фазам.
5. Рекомендация: один агент или несколько, и как их безопасно разделить.
```

## Как использовать

1. Начать новый чат в этом же проекте.
2. Вставить текст из блока выше.
3. Приложить или указать актуальный файл интервью, если он не находится в репозитории.
4. Попросить сначала сделать анализ и план, а не код.

## Рекомендация по агентам

На первом шаге нужен один ведущий агент. Проект сейчас в точке, где параллельная разработка без общей схемы может сломать БД, расписание и финансовую логику.

После согласования PRD и доменной модели можно распараллелить:

- агент по БД и бизнес-правилам;
- агент по UX/UI календаря и рабочих экранов;
- агент по финансам, отчетам и табелям;
- агент по production, безопасности, почте и бэкапам.
