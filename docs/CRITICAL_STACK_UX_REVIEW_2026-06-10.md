# Критический срез проекта RMcodex

Дата: 2026-06-10  
Основание: текущее состояние репозитория, `MIGRATION_REPORT.md`, интервью `интервьюРМ08062026.md`, проверка кода и тестов.

## 1. Текущая стадия

Проект сейчас находится не в стадии "маленький MVP", а в стадии расширенного операционного прототипа:

- Django-приложение уже покрывает расписание, получателей, представителей, специалистов, балансы, подтверждения, документы, согласия, платежи, рекомендации, грантовый отчет и табели.
- Есть сервисный слой, API для календаря, FullCalendar, HTMX, аудит, фоновые задачи, PDF и попытка PyInstaller-сборки.
- Тесты проходят: `python manage.py test` — 40 тестов OK.
- Проект пока не production-ready: есть риски по упаковке, UX, безопасности, офлайн-ассетам и раздвоению конфигураций.

Ключевой вывод: это уже достаточно серьезная Django-система. Переписывать ее на React сейчас рискованнее, чем стабилизировать текущую архитектуру и точечно улучшить интерфейс.

## 2. Что хорошо

- **Django как ядро подходит.** Для 5 администраторов, 300 получателей, 50 специалистов и сложной доменной логики Django дает админку, ORM, миграции, формы, права, тестируемость и быстрый выпуск.
- **Серверный рендеринг подходит аудитории.** Администратору нужен быстрый понятный интерфейс, а не сложная SPA-архитектура. Ошибки форм, сохранение, печать и документы проще делать на Django.
- **FullCalendar уместен.** Расписание действительно требует визуального календаря, фильтров и drag-and-drop. Это правильная зона для JS.
- **SQLite fallback полезен для EXE.** Для демонстрации и одиночного локального запуска SQLite сильно проще, чем переносимый PostgreSQL.
- **Тесты уже есть.** Это важное отличие от хаотичного прототипа: поведение можно стабилизировать.

## 3. Что критично плохо

### 3.1 API был публичным

До правки `/api/appointments/`, `/api/staff/`, `/api/services/` открывались без логина. Это особенно опасно для удаленного туннеля.

Что сделано:

- `operations/api.py` переведен на `NinjaAPI(auth=django_auth, ...)`;
- добавлены регрессионные тесты в `operations/tests.py`;
- подтверждено: анонимные API-запросы теперь получают `401`.

### 3.2 EXE-сценарий пока экспериментальный

Сейчас есть `scripts/launcher.py`, `scripts/build_viewer.py`, `settings_viewer.py`, `RMcodex.spec`, `dist/`, `build/`. Но это еще не надежный продуктовый EXE.

Проблемы:

- `settings_viewer.py` живет отдельно от основных настроек и может разойтись с ними;
- есть лишние зависимости в `settings_viewer.py` (`django_filters`, `django_extensions`, `ninja` как app), которых нет в основном `INSTALLED_APPS`;
- портативный PostgreSQL резко усложняет сборку, вес и поддержку;
- CDN-ассеты ломают офлайн-демо;
- console-окно PyInstaller выглядит технически и может пугать администратора.

Решение: для демонстрации и пилота делать один официальный EXE-профиль: PyInstaller one-dir + SQLite + локальные static assets + автооткрытие браузера. PostgreSQL оставить для серверного контура.

### 3.3 Интерфейс стал перегружаться

После расширения появились документы, согласия, гранты, платежи, рекомендации, табели, массовые переносы. Для слабого пользователя ПК это много пунктов и много равноправных экранов.

Основной UX-риск: администратор не понимает "что делать прямо сейчас". Нужна не просто красивая оболочка, а рабочий поток:

1. "Сегодня / Завтра"
2. "Очередь решений"
3. "Создать занятие"
4. "Получатель"
5. "Деньги / списания"

Остальное должно быть вторым уровнем, а не основным меню.

### 3.4 Фронтенд зависит от CDN

`templates/base.html` тянет Bootstrap, Bootstrap Icons, HTMX, Alpine с внешних CDN. Для EXE, офлайн-демо, слабого интернета и закрытого центра это неправильно.

Нужно:

- положить Bootstrap CSS/JS локально;
- положить Bootstrap Icons локально или заменить на inline/icon-font локально;
- положить HTMX и Alpine локально или убрать Alpine, если он не нужен;
- запретить внешние CDN в базовом шаблоне.

### 3.5 Смешаны несколько стратегий запуска

Сейчас в проекте одновременно:

- Docker + PostgreSQL;
- локальный Python + SQLite fallback;
- переносимая Python demo-папка;
- PyInstaller viewer;
- удаленный туннель.

Это нормально как эксперименты, но плохо как продукт. Для команды и демонстрации нужны 3 официальных режима:

- **Demo EXE:** Windows, SQLite, без Docker, без Python, один запуск.
- **Dev:** Docker Compose + PostgreSQL.
- **Pilot server:** мини-сервер/VPS + Docker Compose + PostgreSQL + backup.

Все остальные варианты должны быть помечены как вспомогательные.

## 4. React: нужен или нет

React не решит главную проблему сам по себе. Главная проблема сейчас — не технология кнопок, а структура пользовательского потока.

### Не рекомендую делать полный React SPA сейчас

Причины:

- придется строить полноценный REST API, авторизацию, CSRF/session или token auth, обработку ошибок, состояние форм;
- документы, PDF, формы, списания и права доступа в Django уже реализуются быстрее;
- упаковка в EXE усложнится: Python backend + Vite build + ассеты + возможный Electron/Tauri;
- для одного центра и 5 администраторов это лишняя сложность.

### Где React может быть полезен

React стоит рассмотреть только как "острова" внутри Django:

- новый продвинутый планировщик расписания;
- drag-and-drop массовых переносов;
- сложный грантовый отчет с закрепленными колонками и интерактивными фильтрами;
- мастер создания курса/серии занятий.

Но сначала нужно довести текущий Django + FullCalendar UI до стабильного уровня.

Рекомендация по стеку: **Django + HTMX + FullCalendar сейчас; React islands позже только для 1-2 сложных экранов.**

## 5. UX/UI: что менять первым

### 5.1 Главный экран администратора

Сделать не "дашборд с карточками", а операционный пульт:

- Сегодня: занятия, отмены, неотмеченные, ожидающие списания.
- Завтра: неподтвержденные, свободные окна, конфликтные места.
- Быстрые действия: новый получатель, новое занятие, принять оплату, отправить расписание.
- Красные задачи наверху, справочники внизу.

### 5.2 Создание получателя

Из интервью: нужен быстрый представитель прямо в форме получателя.

Нужно:

- кнопка "Создать представителя" внутри формы получателя;
- минимальная форма: ФИО получателя, телефон/email если есть, представитель, статус;
- необязательные поля не должны мешать первичному вводу.

### 5.3 Создание занятия

Критический сценарий:

- счет списания должен быть виден всегда;
- счет списания обязателен для активного занятия, если услуга платная/учитываемая;
- после выбора получателя и услуги список счетов должен фильтроваться без переходов;
- после сохранения списания нужен явный результат: "Списано 1 занятие с гранта X".

### 5.4 Расписание

Нужно довести календарь до роли главного рабочего инструмента:

- фильтр по получателю, специалисту, услуге, кабинету;
- понятные цвета статусов: проведено, отменено, предложено, бронь, неявка;
- drag-and-drop с подтверждением и понятной ошибкой;
- создание серии на неделю/месяц по дням недели;
- предупреждение о нерабочем времени специалиста;
- быстрое предложение свободных окон.

### 5.5 Грантовый отчет

Из интервью: таблица должна читаться на экране, не только в Excel.

Нужно:

- sticky header;
- горизонтальный scroll внутри таблицы;
- автоширина колонок по содержимому;
- группировка по источнику/услуге/получателю;
- итоговые строки закрепить визуально.

## 6. EXE: правильная целевая схема

Для демонстрации и теста администратором:

```
RMcodex/
  RMcodex.exe
  data/
    rehab.sqlite3
    media/
  logs/
  _internal/
```

Поведение:

1. Пользователь запускает `RMcodex.exe`.
2. Приложение находит свободный порт.
3. Применяет миграции.
4. Если база пустая — предлагает загрузить демо-данные.
5. Открывает браузер на `http://127.0.0.1:<port>/`.
6. При закрытии окна останавливает локальный сервер.

Не надо для EXE:

- Docker;
- PostgreSQL;
- Redis;
- внешний CDN;
- ручной ввод команд;
- требование Python на компьютере.

Для реального центра позже:

- мини-сервер или VPS;
- Docker Compose;
- PostgreSQL;
- регулярный backup;
- доступ по локальной сети/VPN/HTTPS.

## 8. Решение по стеку

Рекомендованный стек на ближайший этап:

- Backend: Django 5.2 LTS.
- Database для EXE/demo: SQLite.
- Database для пилота/сервера: PostgreSQL.
- Frontend сейчас: Django Templates + HTMX + FullCalendar + локальный Bootstrap/custom CSS.
- Frontend позже: React islands только для сложного планировщика или аналитических таблиц.
- Packaging: PyInstaller one-dir, не Docker для демонстрационного ноутбука.
- Production delivery: Docker Compose на мини-сервере/VPS, не EXE.

Ключевой вывод: **React не нужен как срочная миграция. Срочно нужен UX-редизайн рабочих потоков, локальные ассеты, один понятный EXE-профиль и стабилизация календаря/списаний.**
