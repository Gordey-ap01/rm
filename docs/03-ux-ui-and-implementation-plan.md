## UX-принцип

Это рабочий инструмент администратора, а не лендинг. Интерфейс должен быть плотным, быстрым, с минимальным количеством декоративных элементов. Главный экран - не "добро пожаловать", а список сегодняшних рисков и действий.

## Основные экраны

### 1. Оперативная панель администратора

Показывает:

- сегодня и завтра;
- кто не подтвердил приход;
- отмены и требующие перестановки занятия;
- свободные окна специалистов;
- получатели с низким остатком;
- документы, которые надо собрать;
- новые заявки и заметки.

### 2. Расписание

Режимы:

- день по специалистам;
- день по помещениям;
- карточка дня получателя;
- неделя специалиста;
- планирование серии.

Ключевые взаимодействия:

- drag/drop или быстрый перенос через форму;
- подсветка конфликтов;
- статусы цветом и иконкой;
- быстрый фильтр: специалист, услуга, получатель, источник финансирования;
- кнопка "создать серию";
- кнопка "отправить на согласование";
- кнопка "сформировать завтра".

### 3. Карточка получателя

Вкладки:

- обзор;
- расписание;
- балансы;
- рекомендации;
- заметки;
- документы;
- история посещений;
- контакты представителей.

Главное правило: администратор должен ответить на вопрос представителя "сколько у нас осталось?" за несколько секунд.

### 4. Финансирование

Экраны:

- источники: гранты, фонды, спонсоры, личные деньги;
- распределение по детям;
- остатки;
- срок освоения;
- операции ledger;
- отчеты за период.

### 5. Табель

Показывает специалиста, период, занятия, длительность, статус, засчитывается ли в оплату, расхождения между отметкой специалиста и администратора.

### 6. Документы и формы

Экраны:

- форма сбора данных представителя;
- форма администратора;
- генерация договора;
- журнал согласий;
- загрузка медицинских рекомендаций;
- фото/видео материалы по получателю и проекту.

### 7. Мобильный экран специалиста

Минимум:

- наглядный календарь/график занятий на день и неделю;
- получатель, услуга, время, помещение;
- отметить проведено/не проведено;
- оставить заметку;
- сводка по отработанным занятиям за период;
- подать отсутствие.

## Фазы реализации

### Фаза 0. Уточнение и каркас

Результат: утвержденная модель MVP и локальный dev-каркас.

Задачи:

- зафиксировать список ролей и прав;
- утвердить, что является MVP;
- выбрать hosting policy для ПДн;
- завести Django/PostgreSQL проект;
- настроить миграции, тесты, seed-данные.

Проверка:

- проект запускается локально;
- есть пустая админка;
- есть первые модели справочников.

### Фаза 1. Справочники и карточки

Результат: можно вести получателей, представителей, специалистов, услуги, помещения, заметки.

Задачи:

- Child/Parent/Staff/Service/Room;
- заметки с поиском;
- рекомендации;
- базовые документы и согласия;
- роли админ/руководитель/специалист.

Проверка:

- администратор создает получателя и представителя;
- находит все заметки по получателю;
- специалист видит только разрешенный минимум.

### Фаза 2. Расписание MVP

Результат: можно составлять рабочее расписание без пересечений.

Задачи:

- Appointment и AppointmentSeries;
- статусы занятий;
- PostgreSQL exclusion constraints;
- экран дня/недели;
- создание серии занятий;
- перенос/отмена/неявка;
- предварительное и согласованное расписание.

Проверка:

- невозможно сохранить пересечение получателя;
- невозможно сохранить пересечение специалиста;
- невозможно сохранить пересечение помещения;
- отмененное занятие не блокирует слот;
- серия создается и редактируется.

### Фаза 3. Балансы и оплаты

Результат: остатки занятий/денег считаются автоматически.

Задачи:

- FundingSource;
- BalanceAccount;
- LedgerEntry;
- Payment;
- списание по занятию;
- предупреждение о низком остатке;
- возвраты/корректировки;
- скидки и типы оплат.

Проверка:

- получатель имеет несколько источников одновременно;
- проведенное занятие списывает правильный баланс;
- неявка может списывать занятие по правилу центра;
- остаток на дату совпадает с ledger.

### Фаза 4. Гранты и отчеты

Результат: руководитель видит освоение средств и занятий.

Задачи:

- грантовые проекты и транши;
- распределение по детям;
- правила передачи остатка;
- отчет по источнику за период;
- отчет по детям/услугам/занятиям;
- табель специалистов.

Проверка:

- видно поступило/распределено/израсходовано/осталось;
- можно передать грантовый остаток другому получателю, если разрешено;
- фонд, закрепленный за получателем, нельзя передать другому;
- табель формируется за 2 недели и месяц.

### Фаза 5. Документы и представительские формы

Результат: данные для договора собираются без повторного ручного набора.

Задачи:

- публичная защищенная форма;
- генерация договора;
- журнал согласий;
- ограничение доступа к паспортным данным;
- загрузка рекомендаций врача;
- правила хранения фото/видео.

Проверка:

- представитель отправляет форму;
- администратор сверяет данные;
- договор формируется из шаблона;
- доступ к ПДн видит только разрешенная роль.

### Фаза 6. Уведомления и кабинеты

Результат: меньше ручной рассылки.

Задачи:

- шаблоны сообщений;
- отправка расписания на завтра;
- безопасные ссылки на подтверждение;
- кабинет специалиста;
- ограниченный представительский кабинет.

Проверка:

- администратор видит статус отправки/ответов;
- персональные документы не уходят в мессенджеры;
- специалист отмечает занятие с телефона.

## Что делать первым

Самый быстрый и правильный вертикальный срез:

1. Карточка получателя + представитель + специалист + услуга + помещение.
2. Расписание одного дня с запретом пересечений.
3. Серия занятий и отмена/перенос.
4. Баланс в занятиях по получателю.
5. Табель специалиста из проведенных занятий.

После этого уже подключать гранты, документы и представительские формы.

## Уточнение запуска от 2026-05-14

Так как точной даты нет, но нужно "поскорее", первый рабочий релиз должен быть не полным продуктом, а узким контуром:

1. локальный Django/PostgreSQL;
2. справочники;
3. расписание с защитой от пересечений;
4. карточка получателя;
5. простой баланс занятий;
6. табель специалиста;
7. экран руководителя с остатками и нагрузкой.

Этот контур уже можно использовать параллельно с Excel, пока не будет уверенности для полного перехода.

## Дополнительное уточнение от 2026-05-14

Порядок эксплуатации:

- этап 1: локальный запуск на ноутбуке;
- этап 2: перенос на мини-сервер в центре;
- пользователей одновременно: 2-3;
- специалистам нужен мобильный экран уже в первой версии;
- данные сначала тестовые, затем импорт Excel.
- запуск через Docker;
- интерфейс на русском;
- вход специалиста по логину и паролю.

Из-за этого первый технический milestone:

1. поднять локальный Django/PostgreSQL;
2. создать тестовые seed-данные;
3. дать администратору экран расписания;
4. дать специалисту мобильный экран "календарь, отметки, заметки, сводка";
5. дать руководителю экран "остатки и нагрузка";
6. только после проверки этих экранов писать импорт Excel.
