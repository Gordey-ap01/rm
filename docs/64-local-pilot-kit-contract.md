## Проверяемый результат

1. Комплект собирается из явно указанного Git-коммита и разрешенного перечня
   файлов в новую папку. Локальные `.env`, данные, приватные документы, дампы,
   `.runtime`, виртуальные окружения и посторонние файлы в него не попадают.
2. Собственный Docker Compose проект `rm-pilot-*`: PostgreSQL без публикации
   порта, приложение только на `127.0.0.1:18000`, отдельные хранилища.
   Почта не отправляется наружу. Запуск не требует активного окна Codex.
3. Учебная исходная база содержит разных администратора/руководителя/
   специалистов, вымышленных получателей, счета, программы, каскады и группу.
   Повторное наполнение не сбрасывает пользовательские изменения и не меняет
   пароль. На неизвестной непустой базе команда наполнения отказывает.
4. Запуск, остановка и повторный запуск комплекта сохраняют учебные записи.
   Ни один штатный сценарий не удаляет БД/каталог или Docker volumes.

## Границы файлов и интерфейсы

- `operations/management/commands/seed_pilot.py` и тесты команды: учебные
  данные. Требуются `RM_PILOT_MODE=1`, PostgreSQL, имя БД `rm_pilot_training`
  и пароль `RM_PILOT_PASSWORD` для первого создания пользователей. Явный
  `--date YYYY-MM-DD` задает сегодняшний или будущий учебный день. Известный маркер инициализации
  проверяется до любых повторных записей; он создается в одной транзакции
  с учебными данными. Используется существующая схема, новых миграций нет.
- `rehab_center/settings_pilot.py`: отдельные настройки локального HTTP с
  выключенным DEBUG и запретом реальной отправки писем. Модуль требует явно
  включенного учебного режима и PostgreSQL с именем `rm_pilot_training`.
  Основные настройки рабочего развертывания не меняются.
- `pilot/compose.yaml`, `pilot/Start-Pilot.ps1`, `pilot/Stop-Pilot.ps1`,
  `pilot/README.md`: отдельный запуск и инструкция. Генерируемые локальные
  настройки находятся только внутри новой папки комплекта. Проект и дата
  зафиксированы в `pilot-manifest.json`; пароль создается при первой настройке.
- `scripts/build_pilot.py` и тесты сборки: источник — committed Git tree;
  разрешены только необходимые исходники приложения и файлы запуска.
  Сборка не меняет и не перезаписывает существующую папку; при Windows
  `core.autocrlf` сохраняются committed bytes. Manifest содержит
  полный source commit, версию формата, имя Compose проекта и учебную дату.
- Manifest v1: `format_version` = 1, `source_commit` = полный SHA,
  `project_name` = `rm-pilot-` + первые 12 знаков SHA, `training_date` = ISO-дата,
  `application_url` = `http://127.0.0.1:18000`.
  `file_sha256` содержит SHA-256 каждого включенного файла; запуск и остановка
  проверяют целостность комплекта до изменения Docker-проекта.

Для Windows предусмотрены `START_PILOT.bat` и `STOP_PILOT.bat`, использующие
Windows PowerShell 5.1. Docker Desktop запускается пользователем; скрипты
используют только его проверенный локальный Linux-контекст. Файл блокировки
защищает одновременный запуск/остановку, а метки Compose запрещают управление
одноименным проектом из другой папки. Инициализированную папку не переносить.

Разработчики могут проверять текущие исходники отдельно, но выдаваемый комплект
должен иметь проверяемую связь с зафиксированной версией кода.

## Приемка

- Отказ наполнения на неверном режиме/БД и неизвестной непустой базе.
- Начальная группа создана существующими write-paths; роли различаются.
- Повтор наполнения сохраняет измененные учебные записи и учетные данные.
- Сборка не включает незакоммиченные данные и отказывает при существующем
  назначении; manifest и список файлов соответствуют выбранному commit.
- Реальное поднятие отдельного комплекта, вход разными ролями через браузер,
  сохранение изменения после остановки/повторного запуска.
- Проверка только loopback web binding, отсутствия опубликованного порта БД,
  сохранения пяти существующих контейнеров пользователя.
- Подготовка Docker и загрузка зависимостей выполняются до выезда; возможность
  запуска на другом компьютере и после перезагрузки Windows подтверждается
  отдельной репетицией на компьютере выезда.
