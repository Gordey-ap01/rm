# Контракт среза: PostgreSQL serialization расписания и списаний

Дата: 2026-07-25

Статус: подэтапы A и B завершены

## Выполнение подэтапа A (2026-07-25)

Реализован единый lock/recheck path для настраиваемой вместимости кабинета:

- `operations.schedule_writes.lock_schedule_write()` блокирует затронутые кабинеты
  в порядке `pk`, а при переносе также родительское занятие;
- после ожидания блокировки вместимость повторно проверяется по актуальным
  snapshot-участникам и назначениям специалистов;
- контракт подключен к form create/move, calendar API move, service create/reschedule,
  materialization серии и program wizard;
- override сохраняется только если нарушение действительно осталось после
  повторной проверки; API не возвращает внутренний текст исключений.

Проверено на disposable PostgreSQL 17 двумя `TransactionTestCase`: параллельные
form-save и service-create не могут занять одно последнее место. Итоговый
focused-контур PostgreSQL: `33 passed`. SQLite не заявлен как доказательство
конкурентности и пропускает эти два теста.

## Выполнение подэтапа B (2026-07-25)

Решение о списании теперь имеет единственный штатный write-path:

- `billing.apply_decision()` блокирует занятие, participant, выбранный счет и
  связанные ledger rows; перед записью объекты читаются заново;
- `BillingDecisionForm` вызывает этот сервис через lazy import и больше не
  создает самостоятельные correction-проводки;
- повторный `charge`, в том числе конкурентный, сохраняет один активный debit
  и не меняет остаток второй раз;
- `do_not_charge` добавляет append-only положительную correction-проводку,
  возвращающую остаток счета, и отвязывает прежние записи от занятия. После
  этого payroll/grant fact не видит списание, но audit-след сохраняется.

Проверено SQLite unit/regression и `TransactionTestCase` на disposable
PostgreSQL 17; общий focused-контур A+B: `34 passed`. Browser smoke локального сценария администратора подтвердил:
один debit после «Списать», пустой ledger занятия и восстановленный остаток
после «Не списывать»; mobile `390px` без horizontal overflow и console errors.

## Цель

Доказать на PostgreSQL, что два одновременных действия администратора не могут
превысить вместимость кабинета или создать двойное списание за одно занятие.
Срез не меняет продуктовые правила из `docs/13-*.md` и `docs/14-*.md`: он
делает штатные write-path устойчивыми к гонкам.

## Контекст и граница

PostgreSQL exclusion constraints уже защищают пересечения конкретного
получателя и специалиста. Вместимость кабинета динамическая: она зависит от
настроек кабинета и числа snapshot-участников/назначений. Ее нельзя корректно
выразить существующим простым `EXCLUDE` или `UNIQUE` constraint.

`billing.apply_decision()` выполняется в транзакции, но до среза не блокирует
родительское занятие. Два запроса могут одновременно не увидеть debit и создать
две проводки. `BillingDecisionForm` также использует отдельный старый алгоритм
ledger-коррекций, поэтому не является единым идемпотентным write-path.

В срез не входят:

- изменение тарифов, грантов, payroll или исторических расчетных листов;
- автоисправление старого ledger;
- удаление legacy полей;
- модель бронирования комнат отдельными слотами;
- Excel import и массовые backfill.

## Решение

### 1. Вместимость кабинета

Перед любым штатным созданием, изменением или переносом занятия с кабинетом:

1. в одной `transaction.atomic()` блокировать строки старого и целевого
   кабинетов через `select_for_update()`, всегда по возрастанию `pk`;
2. повторно проверить актуальную вместимость через
   `appointment_group_conflicts()` уже после блокировки;
3. сохранить занятие и snapshot-строки до освобождения блокировки;
4. при явном `room_limit_override` сохранить существующий audit record, но все
   равно брать блокировку и повторно классифицировать нарушение.

Блокировка нужна только для кабинетов. Конкретные получатели и специалисты
остаются дополнительно защищены действующими PostgreSQL exclusion constraints.
Сериализация на строке кабинета намеренно консервативна: центр имеет низкую
частоту записи, а корректность вместимости важнее параллельности записей в
одном помещении.

Штатные write-path первого подэтапа:

- `AppointmentForm.save()`;
- `AppointmentMoveForm.save()`;
- calendar API move;
- `operations.services.appointments.create_appointment()` и `reschedule()`;
- materialization series и program wizard.

### 2. Идемпотентное списание

Штатный путь решения по списанию должен:

1. блокировать `Appointment`, затем выбранного participant, счет и связанные
   ledger rows в предсказуемом порядке;
2. заново получать объекты внутри транзакции, не использовать переданный
   устаревший instance;
3. создавать или обновлять ровно одну активную debit-проводку для выбранного
   участника/legacy занятия;
4. при `do_not_charge` сохранить историю, добавить correction для возврата
   остатка и отвязать прежние записи от занятия;
5. использовать этот сервис из `BillingDecisionForm`, а не второй алгоритм
   добавления correction-проводок.

В этом срезе не добавляется partial unique constraint на `LedgerEntry`.
Старые данные и audit tests намеренно допускают несколько debit-записей для
диагностики. Такой constraint допустим только после отдельного preflight и
согласованной политики исторической коррекции; сначала защищается весь штатный
write-path блокировкой родителя.

## Подэтапы

### A. `postgresql-room-capacity-serialization`

**Acceptance criteria:**

- две формы, одновременно прошедшие первоначальную валидацию, не могут занять
  последнее место одного кабинета;
- одна транзакция сохраняется, вторая после ожидания получает понятную ошибку
  вместимости; итоговые counts не превышают лимит;
- перенос, drag-and-drop API, сервисный create/reschedule и materialization не
  обходят тот же lock/recheck contract;
- override сохраняет причину и автора, но не отменяет блокировку;
- PostgreSQL `TransactionTestCase` проверяет гонку; SQLite покрывает обычные
  пути без заявления о конкурентности.

### B. `postgresql-billing-decision-idempotency`

**Acceptance criteria:**

- два конкурентных `charge` для одного participant/занятия оставляют одну
  связанную debit-проводку и один финансовый факт;
- повтор того же решения не меняет баланс второй раз;
- форма списания вызывает единый сервис и сохраняет participant-level правило
  для групп;
- `do_not_charge` не оставляет активный debit, создающий ложный payroll/grant
  факт, и возвращает остаток соответствующего счета;
- PostgreSQL `TransactionTestCase` покрывает конкурентный charge и
  `financial_integrity` не находит ошибку в штатном сценарии.

После A и B выполняется цельный desktop/mobile сценарий администратора:
создать запись -> отметить проведение -> принять решение о списании -> увидеть
ровно одну проводку и актуальный остаток.

## Тесты и эксплуатационная безопасность

- Не считать SQLite проверкой блокировок PostgreSQL.
- Использовать disposable PostgreSQL 17, применяя миграции с пустой базы.
- Перед production rollout запустить существующий financial-integrity audit;
  срез не меняет и не удаляет исторические проводки.
- При `IntegrityError`, `OperationalError` или `ValidationError` транзакция не
  должна оставлять частично созданное занятие, snapshot или ledger entry.
- После любого UI-изменения выполнить browser smoke desktop/mobile; при
  чисто сервисном подэтапе browser QA не обязателен.

## Владение и параллельность

Один ведущий DB owner меняет сервисы записи, `operations/models.py` при
необходимости и migration chain. После фиксации service contract отдельный
agent может подготовить только PostgreSQL tests в новом непересекающемся файле,
но не меняет модели, forms, `billing.py`, `scheduling.py` или migrations.
