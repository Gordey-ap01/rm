# Контракт среза: browser-приемка рабочих ролей

Дата: 2026-07-26

Статус: implemented

## Основание

`docs/01-prd.md`, `docs/51-payroll-director-approval-contract.md`,
`docs/52-payroll-payout-lifecycle-contract.md`,
`docs/53-operational-e2e-acceptance-contract.md` и
`docs/54-production-preflight-contract.md` доказали доменные правила,
полномочия и production-путь. Этот срез подтверждает, что ключевые роли могут
выполнить их через настоящий браузер, а не только через service- и view-тесты.

## Граница среза

Входит:

1. Desktop-путь администратора: очередь, экран «Завтра» и просмотр расчетного
   листа без финансовых команд руководителя.
2. Desktop-путь руководителя: утвержденный расчетный лист передается в выплату,
   затем через UI фиксируется один полный банковский платеж с реквизитом.
3. Мобильный путь специалиста на viewport `390x844`: вход в кабинет,
   календарь/рабочий график/заявка на отсутствие доступны без horizontal
   overflow.
4. Для каждого сценария: HTTP-ответы UI `200`, отсутствие console/page errors
   и ответов `4xx`/`5xx` на загружаемых ресурсах, проверка ширины документа и
   визуальный просмотр desktop/mobile снимков.

Не входит:

- новая модель, миграции, изменение финансовых правил или production-данных;
- обход UI прямыми запросами: backend authorization уже покрыта service/view
  тестами срезов `51` и `52`;
- все экраны и все комбинации ролей, тест на физическом телефоне или
  приемочный пилот центра;
- хранение screenshots, логинов, паролей, cookies или персональных данных.

## Изолированная среда

Приемка выполнена на временной SQLite-базе вне репозитория, с обезличенными
фикстурами трех ролей и одним утвержденным расчетным листом. После проверки
временная БД, лог сервера, fixture и settings-модуль удалены. Основная БД,
production и пользовательский профиль браузера не использовались.

В управляемом Playwright-окружении отсутствовал скачанный Chromium, поэтому
Playwright запустил локально установленный Chrome в новом изолированном
контексте. Это способ выполнения локальной приемки, а не новая runtime-
зависимость продукта.

## Сценарии и критерии

| Роль и экран | Действие | Критерий |
| --- | --- | --- |
| Администратор, desktop | Открыть `/work-queue/` и `/tomorrow/` | Оба рабочих экрана доступны, заголовок соответствует экрану, документ не шире viewport. |
| Администратор, расчетный лист | Открыть утвержденный лист | Видны данные листа и история, но отсутствуют команды `send` и `record_payout`. |
| Руководитель, расчетный лист | Передать утвержденный лист в выплату | Команда передачи доступна только до перехода; после отправки появляется форма фактической выплаты. |
| Руководитель, расчетный лист | Зафиксировать полную выплату | После POST нет повторных финансовых команд, лист переживает reload, видны реквизит и два события истории: передача и выплата. |
| Специалист, mobile | Открыть `/specialist/` на `390x844` | Кабинет загружается, один заголовок профиля виден, `document` и `body` не шире viewport. |

## Результат приемки

Все критерии выполнены 2026-07-26.

- Администратор открыл очередь, «Завтра» и расчетный лист; директорские
  финансовые действия не отрисованы.
- Руководитель провел расчетный лист через `approved -> sent -> paid` только
  UI-командами. После reload сохранились финальный статус, реквизит платежа и
  две lifecycle-записи.
- Мобильный кабинет специалиста на ширине `390px` имеет `scrollWidth ==
  viewportWidth`; desktop-экраны также не имеют горизонтального переполнения.
- Во всех трех изолированных сценариях не зафиксированы console/page errors и
  ответы `4xx`/`5xx`.
- Desktop и mobile снимки просмотрены в ходе запуска; пересечений текста,
  скрытых команд и критичных нарушений компоновки не обнаружено.

## Продолжение

При каждом изменении пользовательского пути выполнять targeted browser smoke
для измененной роли. Перед запуском центра нужны проверка на реальном телефоне
и пилот на обезличенных рабочих сценариях, а не повторение этой временной
фикстуры.
