## Ключевые решения после уточнений

1. Занятие может быть индивидуальным или групповым.
2. Групповое занятие может включать несколько получателей.
3. В одном групповом занятии может быть несколько специалистов.
4. Индивидуальное занятие блокирует специалиста на это время для других занятий.
5. Групповое занятие не создает отдельное занятие на каждого ребенка. Дети добавляются как участники одной сессии до лимита.
6. Родители и сопровождающие не учитываются во вместимости кабинета.
7. Кабинет должен отдельно ограничивать количество специалистов и количество получателей.
8. Администратор может сам сделать одноразовое разрешение на нарушение правил кабинета через удержание кнопки.
9. Основной представитель подписывает договор. Дополнительные представители могут получать расписание, если включен флажок.
10. Зарплатные правила назначает руководитель.
11. Для групп руководитель задает, как считать зарплату: один раз за занятие, по каждому списанному получателю, фиксированной суммой или другим утвержденным правилом.
12. Если в занятии несколько специалистов, руководитель задает начисление каждому специалисту.
13. Начисление зарплаты происходит при решении администратора `списать`, а не только при статусе `проведено`.
14. Грантовая квота задается сначала на услугу/направление, потом распределяется между специалистами. При необходимости должен быть быстрый сценарий сразу `специалист + количество занятий`.
15. Списание при переносе остается на решении администратора.
16. Желательно вести расписание, балансы, зарплаты, гранты, расходы и документы в едином контуре, но реализовывать это вертикальными срезами.

## Реализовано в первых срезах

По состоянию на текущую ветку:

- добавлены `RecipientRepresentative`, `AppointmentParticipant`, `AppointmentStaffAssignment`, `AppointmentRoomOverride`;
- добавлены кабинетные поля `limit_staff_count`, `max_staff_count`, `limit_recipient_count`, `max_recipient_count`, `allow_group_sessions`;
- `Appointment` получил `session_type` и `title`;
- расписание, форма занятия, API календаря и мобильный кабинет специалиста переведены на участников и назначения специалистов;
- списание в группах поддерживает решение по конкретному `AppointmentParticipant`;
- табель специалиста считает назначения через `AppointmentStaffAssignment`;
- добавлен справочник `StaffCompensationRule` и расчет суммы к начислению в табеле;
- ставки специалистов могут ограничиваться диапазоном длительности занятия;
- добавлены `FundingServiceQuota` и `FundingStaffAllocation`;
- grant report показывает квоты по услугам, распределение между специалистами и ledger-backed факт по списанным занятиям;
- добавлены persisted-сущности `PayrollAccrual`, `PayrollSheet`, `PayrollSheetLine`;
- табель и persisted payroll учитывают ставку `FundingStaffAllocation.session_pay_amount` как приоритетную грантовую ставку;
- добавлен рабочий справочник `Service` вне Django admin: создание, редактирование, архивирование и восстановление услуг/направлений;
- добавлен рабочий справочник `StaffMember` вне Django admin: создание, редактирование, привязка пользователя, архивирование и восстановление специалистов;
- добавлен рабочий справочник `FundingSource` вне Django admin: создание, редактирование, архивирование и восстановление источников финансирования;
- добавлен рабочий справочник `StaffCompensationRule` вне Django admin: создание, редактирование и включение/отключение ставок специалистов;
- `StaffCompensationRule` расширен `session_scope`, `group_pay_policy`, `group_fixed_amount`, а `PayrollAccrual` хранит snapshots принципа группового начисления, числа списанных участников и расчетных единиц;
- добавлены UI-сценарии создания квоты услуги и распределения квоты по специалисту вне Django admin;
- добавлены UI-сценарии редактирования и удаления грантовых квот/распределений; удаление квоты блокируется, если под ней уже есть распределения;
- факт по грантовому распределению специалиста считается с учетом периода конкретного распределения, чтобы смена специалиста/периода не задваивала факт;
- быстрый сценарий `специалист + количество занятий` поддержан через `FundingStaffAllocation` без обязательной `service_quota`;
- прямое распределение остается отдельной видимой строкой, даже если в том же
  периоде есть квота этой услуги; решение `Списать` без debit-проводки не
  увеличивает факт и выводится как нарушение финансовой целостности;
- добавлен рабочий UI кабинетов с настройками лимитов специалистов, получателей и разрешения групповых занятий;
- hold-to-confirm для одноразового нарушения лимитов кабинета проходит form validation и model validation при сохранении из `AppointmentForm`; прямое сохранение модели без такого намеренного флага не обходит лимит.
- расчет занятости кабинета использует общий helper: считает `AppointmentParticipant`/`AppointmentStaffAssignment`, а для занятий без snapshot-строк добирает legacy `Appointment.child`/`Appointment.staff_member`, чтобы смешанные переходные данные не занижали лимиты кабинета в форме, model validation, `find_overlaps()` и API drag-and-drop.
- API drag-and-drop при partial snapshot различает конфликтную проверку и расчет входящей вместимости: конфликты проверяются консервативно с учетом legacy-полей, но количество переносимых получателей/специалистов берется из фактических snapshot-строк, а legacy используется только как fallback при их отсутствии.
- API drag-and-drop не переиспользует старые `staff_availability_override` / `AppointmentStaffAssignment.override_availability` как разрешение на новый слот: доступность специалистов проверяется заново, а при успешном переносе на доступное время устаревшие override-флаги очищаются.
- карточка получателя показывает несколько представителей и флажок получения расписания;
- отправка подтверждений учитывает представителей с `receives_schedule=true` у всех участников группового занятия;
- `AppointmentConfirmation` хранит ссылку на конкретный `AppointmentParticipant` для согласования представителя/получателя и ссылку на конкретный `AppointmentStaffAssignment` для согласования специалиста;
- карточка получателя и список получателей учитывают групповые занятия через `AppointmentParticipant`;
- dashboard считает нагрузку специалистов через `AppointmentStaffAssignment`.
- "Завтра", дашборд и очередь администратора отображают групповые занятия через участников и назначения специалистов;
- очередь "прошли без отметки" учитывает частично отмеченные группы, где у отдельного участника еще `attendance_status=unknown`;
- быстрые списания в очереди администратора отключены для групповых занятий: решение принимается в карточке занятия по каждому `AppointmentParticipant`.
- карточка группового занятия позволяет привязать блок программы и номер занятия отдельно к каждому `AppointmentParticipant`;
- счетчики блока программы `scheduled_count` и `paid_count` считают строки `AppointmentParticipant`, а не только старое поле `Appointment.program_block`.
- лимит брони сверх доступной оплаты в мастере каскада также считает активные строки `AppointmentParticipant` и использует старое поле `Appointment.program_block` только как fallback для записей без snapshot-участников.
- карточка занятия и форма переноса показывают занятые окна-кандидаты для ручного сдвига расписания, если свободных окон переноса нет.
- добавлен `GrantRecipientAllocation`: выделение грантовых занятий получателю со связкой на `BalanceAccount`;
- `django-auditlog` регистрирует новые критичные сущности расписания, финансов, грантов, ставок и persisted payroll.
- добавлен безопасный preview-импорт получателей из `.xlsx/.csv/.tsv`: распознавание колонок, ошибки, предупреждения о дублях, без записи в БД.
- карточка занятия показывает auditlog-историю изменений по самому занятию и связанным участникам, назначениям специалистов, ledger-операциям и подтверждениям.
- мобильный кабинет специалиста учитывает `StaffMember.can_use_mobile`: при отключенном доступе обычный специалист получает 403 и не может отправить прямую POST-отметку занятия.
- API календаря и справочников под `/api/` требует `is_staff`, чтобы специалист не мог получить общий календарь через прямой запрос.
- API-перенос занятия через drag-and-drop проверяет конфликты всех `AppointmentParticipant` и всех `AppointmentStaffAssignment`, а также отпуск/отгул/доступность каждого назначенного специалиста, а не только legacy-поля `child`/`staff_member`.
- экран "Завтра" считает очередь списаний по `AppointmentParticipant`: полностью решенная группа не остается в списке только из-за legacy `Appointment.billing_decision=undecided`.
- грант-отчет по счетам считает `appointments_count`, `planned_count` и `completed_count` также по `AppointmentParticipant.billing_account`, чтобы групповые участники попадали в отчет руководителя.
- грант-отчет считает opening/closing на границах выбранного периода,
  не складывает рубли с занятиями, включает архивные счета и доступен
  администратору только для чтения; плановые сущности изменяет руководитель.
- факт грантовых квот/распределений считает источники финансирования по `AppointmentParticipant.billing_account`, если у занятия уже есть участники; legacy `Appointment.billing_account` применяется только для старых занятий без участников.
- табель и persisted payroll не применяют грантовую или источниковую ставку к групповому занятию со смешанными источниками финансирования у списанных участников: такая строка считается только по общей подходящей ставке специалиста и получает примечание о смешанных источниках.
- persisted payroll для группового занятия с несколькими списанными участниками не привязывает начисление к одному произвольному `AppointmentParticipant` или `LedgerEntry`; если источник финансирования общий, он сохраняется на начислении как общий контекст сессии.
- табель показывает явную строку ставки для `StaffCompensationRule` и для грантовой ставки `FundingStaffAllocation.session_pay_amount`; расчетный лист показывает источник финансирования и snapshot-ставку каждой строки.
- табель не падает, если занятие списано, а подходящая ставка специалиста не задана: строка остается видимой как оплачиваемая по факту списания, сумма равна 0, в примечании указывается отсутствие ставки.
- строки табеля показывают решение списания из `AppointmentParticipant`, если snapshot-участники есть: для одного участника это его статус, для группы - сводка по `списать`/`не списывать`/`не решено`, а не legacy `Appointment.billing_decision`.
- табель специалиста и persisted payroll учитывают legacy-занятия без `AppointmentStaffAssignment` даже в смешанном периоде с новыми назначениями, но исключают нормализованные строки, чтобы не задвоить занятия.
- мобильный кабинет специалиста показывает legacy-занятия без `AppointmentStaffAssignment` через временную display-строку, пока переходная миграция старых данных не завершена.
- сервис переноса не синхронизирует legacy-участника на исходном занятии, если фактические snapshot-участники уже отличаются от старого `Appointment.child`; это защищает partial snapshot от повторного добавления лишнего получателя.
- форма ручного переноса занятия использует тот же контракт для нового занятия: если фактические `AppointmentParticipant` уже отличаются от старого `Appointment.child`, новое занятие получает legacy-получателя и счет из snapshot-участника, а не добавляет устаревшего получателя обратно.
- форма ручного переноса группового занятия разрешает осознанный выход вне графика для всех назначенных специалистов, включая ассистентов; новое занятие сохраняет `override_availability` на каждом недоступном `AppointmentStaffAssignment`.
- API drag-and-drop переноса обновляет snapshot-время существующих `AppointmentParticipant`/`AppointmentStaffAssignment` без восстановления legacy-участника, если partial snapshot уже является источником правды.
- общая `Appointment.save()`-синхронизация не восстанавливает legacy `child/staff_member`, если snapshot-строки уже есть и legacy-связь явно удалена из них; для записей без snapshot-строк fallback продолжает создаваться.
- `Appointment.save()` и `AppointmentForm._sync_participants()` при наличии существующих `AppointmentParticipant` не перезаписывают их participant-level решения списания, счет, посещаемость, программу и номер из legacy-полей занятия; обычное сохранение занятия обновляет только snapshot-время и статус. Для существующих `AppointmentStaffAssignment` прямой `Appointment.save()` также не перезаписывает роль и признак выхода вне графика.
- `AppointmentForm._sync_staff_assignments()` сохраняет роль существующего `AppointmentStaffAssignment`, если основной специалист не менялся. Роль пересчитывается только при явной смене основного специалиста или добавлении нового назначения.
- `AppointmentForm` при обычном редактировании partial snapshot не восстанавливает устаревшие legacy `Appointment.child`/`Appointment.staff_member`, если они уже отсутствуют среди фактических `AppointmentParticipant`/`AppointmentStaffAssignment`; multi-select участников и специалистов остается источником правды.
- табель и persisted payroll игнорируют legacy `Appointment.billing_decision=CHARGE`, если у занятия уже есть `AppointmentParticipant` и среди участников нет списания со счетом.
- `billing.apply_decision()` для partial snapshot хранит списание на `AppointmentParticipant` и ledger, не записывая счет участника в legacy `Appointment.billing_account`, если этот счет не принадлежит legacy `Appointment.child`.
- dashboard/work queue и `tomorrow_overview()` ищут нерешенные списания по `AppointmentParticipant.billing_decision`, если snapshot-участники есть; legacy `Appointment.billing_decision` используется только для старых записей без участников.
- work queue показывает посещаемость одиночного snapshot-участника из `AppointmentParticipant.attendance_status`; legacy `Appointment.attendance_status` остается fallback для старых занятий без участников.
- быстрые списания в work queue для одиночного snapshot-участника берут счет из `AppointmentParticipant.billing_account`; для нескольких участников быстрый action скрыт, чтобы администратор принял решение по каждому участнику.
- `BillingDecisionForm` без явного `participant_id` автоматически выбирает единственного `AppointmentParticipant`; это сохраняет быстрые действия и карточку одиночного snapshot-занятия на participant-level списании.
- для занятия с несколькими `AppointmentParticipant` списание без конкретного `participant_id` запрещено на уровне формы и сервиса, чтобы случайно не списать первого участника группы.
- старые helper'ы синхронизации ledger (`forms.sync_ledger_to_target()` и `appointments.sync_ledger_for_decision()`) также запрещают прямой вызов для занятия с несколькими `AppointmentParticipant`; перед записью проводки нужен явный участник.
- `record_attendance()` синхронизирует отметку специалиста в существующие `AppointmentParticipant`: статус занятия, статус посещения, заметку, время отметки и snapshot-время, чтобы групповые и переходные занятия не расходились между legacy-полями и нормализованными строками.
- мобильная POST-отметка специалиста создает `AppointmentParticipant` из legacy `Appointment.child` и `AppointmentStaffAssignment` из legacy `Appointment.staff_member` только если у занятия еще нет соответствующих snapshot-строк; при существующем partial snapshot старые legacy-связи не добавляются обратно.
- `Appointment.__str__()` учитывает групповые занятия: прямой вывод объекта использует название группы или список `AppointmentParticipant`, а не только legacy `Appointment.child`.
- карточка занятия для ровно одного snapshot-участника показывает списание и счет из `AppointmentParticipant`, а legacy `Appointment.billing_decision`/`Appointment.billing_account` остаются fallback только для записей без участников.
- карточка занятия показывает кнопку пополнения только для однозначного счета: legacy-занятие без участников или ровно один `AppointmentParticipant`; для группы из нескольких участников общий счет не выбирается.
- API календаря использует `Appointment.title` как название группового события, если оно задано; счетчик `Группа (N)` остается запасной подписью для групп без названия.
- API календаря для ровно одного snapshot-участника берет `billingAccountId` и `accountColor` из `AppointmentParticipant.billing_account`; для нескольких участников единый счет события не выбирается.
- API календаря для одиночного snapshot-занятия также отдает `childId` и `staffId` из фактических snapshot-строк, чтобы технические поля совпадали с отображаемым получателем и специалистом.
- дефолтный текст письма-согласования для представителя/получателя конкретного участника группы сужается до этого `AppointmentParticipant`; вручную измененный текст администратора не перезаписывается.
- если один представитель получает расписание для нескольких участников одной группы, форма согласования показывает отдельную цель отправки на каждого `AppointmentParticipant`, чтобы не потерять второго ребенка из-за дедупликации email.
- массовая отмена/перенос по специалисту использует тот же принцип: цели уведомлений представителям строятся по участникам группы и не дедуплицируются по одному представителю, если он получает расписание для нескольких детей.
- очередь администратора по email-согласованиям показывает целевого `AppointmentParticipant` или целевое `AppointmentStaffAssignment`, если подтверждение было отправлено конкретному участнику группы или конкретному специалисту.
- список получателей считает занятия по объединению legacy `Appointment.child` и нормализованных `AppointmentParticipant`, исключая двойной счет обычного индивидуального занятия.
- карточка занятия показывает вычисляемую сводку списаний по `AppointmentParticipant`, чтобы группа с уже принятыми решениями не выглядела как полностью нерешенная из-за legacy `Appointment.billing_decision`.
- карточка занятия показывает вычисляемую сводку посещаемости по `AppointmentParticipant`; legacy `Appointment.attendance_status` используется только для старых занятий без участников.
- карточка занятия ищет "другие занятия получателя" по фактическим `AppointmentParticipant.child`, если участники есть; legacy `Appointment.child` используется только для старых занятий без участников.
- блок "Завтра" на dashboard для одиночного snapshot-участника/назначения также использует `AppointmentParticipant` и `AppointmentStaffAssignment`; legacy `Appointment.child/staff_member` остается только fallback.
- экран "Завтра" выводит не только счетчики, но и рабочие строки email-согласований с целевым участником/специалистом и строки низких балансов.
- экран "Завтра" использует общий доменный флаг `BalanceAccount.is_low_balance`, а не отдельный жесткий порог остатка, чтобы низкие балансы совпадали с dashboard/очередью.
- факт по `GrantRecipientAllocation` в grant report считается только по списаниям связанного счета в пределах дат выделения и только по услуге этого выделения.
- агрегаты grant report по `FundingServiceQuota` ограничены датами самой квоты, а агрегаты прямого распределения `FundingStaffAllocation` без квоты считают только занятия назначенного специалиста в датах распределения.
- подсказки переноса при частично заполненных snapshot-участниках дополнительно учитывают legacy `Appointment.child`, чтобы переходные данные не пропускали конфликт получателя.
- PostgreSQL exclusion constraints для пересечений `AppointmentParticipant` и `AppointmentStaffAssignment` добавлены в миграции `0011`;

Пока не реализовано как отдельные persisted-сущности:

- автоматические цепочки согласования каскадного переноса расписания.

## Главный вывод по текущей модели

Текущая модель `Appointment` как "один получатель + один специалист + один кабинет" больше не соответствует требованиям. Ее нельзя надежно расширить только полями `is_group` и `capacity`, потому что:

- у одного занятия может быть много получателей;
- у одного занятия может быть много специалистов;
- списание баланса должно быть индивидуальным по получателю;
- зарплата должна начисляться индивидуально по специалисту;
- кабинетные ограничения считаются по агрегату: сколько специалистов и получателей уже находятся в кабинете в пересекающееся время;
- текущий PostgreSQL exclusion constraint по кабинету запрещает любое пересечение и конфликтует с кабинетами вместимостью больше 1.

Нужна нормализация: отдельная сущность сессии, отдельные участники-получатели, отдельные назначения специалистов.

## Целевая модель расписания

Для минимизации миграционного риска можно оставить имя `Appointment`, но изменить его смысл: это не "занятие одного ребенка", а "сессия занятия во времени".

### `Appointment`

Смысл: сессия занятия в расписании.

Основные поля:

- `service`
- `room`
- `starts_at`
- `ends_at`
- `status`: draft, proposed, reserved, confirmed, completed, cancelled, no_show, rescheduled
- `session_type`: individual, group
- `title`
- `program_block`, если сессия создана из программы
- `series`, если сессия создана из серии
- `source_appointment`, если сессия является переносом
- `admin_note`
- `created_by`
- `updated_by`

Правило: `Appointment` больше не должен быть единственным источником правды по получателю, специалисту, списанию и зарплате.

Переходно старые поля `child`, `staff_member`, `billing_account`, `billing_decision`, `attendance_status`, `sequence_number` могут оставаться до завершения миграции, но должны считаться deprecated после ввода новых таблиц.

### `AppointmentParticipant`

Смысл: один получатель внутри сессии занятия.

Основные поля:

- `appointment`
- `child`
- `attendance_status`: unknown, attended, missed, excused
- `billing_decision`: undecided, charge, do_not_charge
- `billing_account`
- `price_snapshot`
- `program_block`
- `sequence_number`
- `source_participant`, если это перенос конкретного участника
- `admin_note`
- `specialist_note`
- `marked_by_staff_at`
- `starts_at_snapshot`
- `ends_at_snapshot`

`starts_at_snapshot` и `ends_at_snapshot` нужны для надежных PostgreSQL exclusion constraints без JOIN к `Appointment`.

Ограничения:

- уникальность `appointment + child`;
- активный получатель не может быть в двух активных сессиях с пересечением времени;
- `billing_account` должен принадлежать этому `child`;
- `billing_account` должен подходить к услуге занятия;
- `sequence_number` уникален внутри `program_block + child`, если используется нумерация курса.

### `AppointmentStaffAssignment`

Смысл: назначение специалиста на сессию.

Основные поля:

- `appointment`
- `staff_member`
- `role`: primary, assistant, substitute, observer
- `pay_rule`
- `pay_amount_snapshot`
- `pay_mode_snapshot`
- `starts_at_snapshot`
- `ends_at_snapshot`
- `override_availability`
- `override_reason`

Ограничения:

- уникальность `appointment + staff_member`;
- специалист не может быть назначен на две разные активные сессии в пересекающееся время, кроме явного одноразового override;
- approved `TimeOffRequest` блокирует назначение, кроме явного override.

### `AppointmentRoomOverride`

Смысл: одноразовое разрешение администратора на нарушение правил кабинета.

Основные поля:

- `appointment`
- `override_type`: staff_limit, recipient_limit, exclusive_room, room_inactive, other
- `reason`
- `created_by`
- `created_at`

Правило UX: если ручное создание занятия нарушает кабинетные правила, система показывает предупреждение и две безопасные команды:

- перейти к настройкам кабинета;
- удержать кнопку и создать одноразовое разрешение с причиной.

## Кабинеты и вместимость

Текущий `Room.capacity` слишком общий. Нужны явные поля.

### `Room`

Добавить или заменить:

- `limit_staff_count`: boolean
- `max_staff_count`: positive integer
- `limit_recipient_count`: boolean
- `max_recipient_count`: positive integer
- `allow_group_sessions`: boolean
- `is_active`
- `color`

Смысл:

- если `limit_staff_count = true`, система считает специалистов в пересекающихся активных сессиях этого кабинета;
- если `limit_staff_count = false`, количество специалистов не ограничивается;
- если `limit_recipient_count = true`, система считает получателей в пересекающихся активных сессиях этого кабинета;
- если `limit_recipient_count = false`, количество получателей не ограничивается;
- родители/сопровождающие не считаются;
- индивидуальные занятия по-прежнему могут пересекаться в одном кабинете, если правила кабинета это разрешают.

### `ServiceRoomRule`

Для некоторых услуг нужны дополнительные ограничения.

Поля:

- `service`
- `room_type`
- `requires_exclusive_room`
- `allow_group`
- `default_group_capacity`
- `notes`

Если `requires_exclusive_room = true`, то даже большой кабинет должен быть занят только одной сессией, если администратор не сделал override.

## Представители

Текущая связь `Child.primary_parent` недостаточна.

### `RecipientRepresentative`

Смысл: связь получателя и представителя.

Поля:

- `child`
- `representative`
- `relationship_type`: mother, father, grandmother, grandfather, guardian, other
- `is_primary`
- `signs_contract`
- `receives_schedule`
- `is_payer`
- `notes`
- `created_at`
- `updated_at`

Ограничения:

- у получателя должен быть максимум один `is_primary = true`;
- у получателя должен быть максимум один `signs_contract = true`, если договор подписывает один человек;
- расписание отправляется всем представителям с `receives_schedule = true`;
- взрослый получатель может не иметь представителя или может быть связан с представителем по отдельному правилу.

Переход:

- существующий `Child.primary_parent` мигрировать в `RecipientRepresentative(is_primary=true, signs_contract=true, receives_schedule=true)`;
- поле `primary_parent` оставить временно для совместимости UI, потом удалить или заменить computed-доступом.

## Программы, каскады, блоки, серии

Текущие `TreatmentProgram`, `ProgramBlock`, `AppointmentSeries` можно сохранить, но нужно уточнить ответственность.

### `TreatmentProgram`

Смысл: программа занятий получателя после консультации.

Поля в целом подходят.

### `ProgramBlock`

Смысл: блок/каскад внутри программы по услуге или направлению.

Дополнить:

- `planned_sessions`
- `group_allowed`
- `default_session_type`
- `balance_account`
- `funding_allocation`

Нумерация занятий должна жить не на `Appointment`, а на `AppointmentParticipant`, потому что в групповой сессии у разных детей могут быть разные программы и разные номера занятий.

Текущее состояние: это уже реализовано для карточки группового занятия через `AppointmentParticipant.program_block` и `AppointmentParticipant.sequence_number`. Старые поля `Appointment.program_block` и `Appointment.sequence_number` остаются переходным слоем для индивидуальных занятий, мастера расписания блока и обратной совместимости существующих экранов.

Мастер расписания каскада покрыт проверкой, что созданные занятия получают `program_block` и `sequence_number` на уровне `AppointmentParticipant`, а не только на legacy `Appointment`.

### `AppointmentSeries`

Смысл: правило генерации сессий.

Дополнить:

- `session_type`
- `default_participants`
- `default_staff_assignments`
- `max_participants`
- `room_rule_snapshot`

Серия может создавать групповые сессии и добавлять участников в уже существующую групповую сессию, если совпадают услуга, время, кабинет и лимиты.

Текущее состояние: старая `AppointmentSeries.materialize_series()` остается legacy-механизмом, но уже не обрывает всю серию при конфликте отдельного слота через `AppointmentParticipant`/`AppointmentStaffAssignment`; конфликтный день пропускается, следующие валидные дни создаются через обычную model validation.

## Переносы и отмены

Текущее состояние:

- свободные окна для переноса подбираются с учетом специалиста, кабинета, получателя и рабочего графика;
- если свободных окон нет, карточка занятия и форма переноса показывают занятые окна-кандидаты с ссылками на конфликтующие занятия;
- перенос группового занятия сохраняет `AppointmentParticipant`, `AppointmentStaffAssignment`, `session_type`, название и привязки участников к блокам программы;
- подсказки свободных окон и занятых окон-кандидатов для группового занятия проверяют всех участников и всех назначенных специалистов;
- исходные участники и назначения при переносе синхронно получают `appointment_status=rescheduled`, чтобы счетчики каскадов не удваивали перенесенную историю;
- отмена день-в-день требует явного подтверждения, что решение по списанию будет принято отдельно;
- это пока не автоматический каскадный перенос: администратор вручную решает, какое занятие сдвигать и списывать ли исходную отмену день-в-день.

Следующий уровень модели, если потребуется автоматизация:

- `ScheduleShiftProposal`: предложение цепочки переносов;
- `ScheduleShiftProposalItem`: конкретное занятие, которое надо перенести или согласовать;
- цепочка обязательных согласующих по специалисту, представителю или получателю поверх отдельных `AppointmentConfirmation`;
- фиксация причины и решения по списанию для каждого исходного занятия.

## Балансы и списания

Базовое решение `BalanceAccount + LedgerEntry` остается правильным.

Ключевое изменение: списание должно ссылаться не просто на `Appointment`, а на `AppointmentParticipant`, потому что в группе один ребенок может быть списан, другой нет.

### `LedgerEntry`

Добавить:

- `appointment_participant`
- `price_snapshot`
- `source_payment`
- `source_transfer`
- `source_conversion`

Правила:

- `LedgerEntry.appointment` можно оставить переходно;
- новое списание занятия должно ссылаться на `AppointmentParticipant`;
- сумма списания в рублях фиксирует цену на момент списания;
- спорные случаи не списываются автоматически;
- решение `charge/do_not_charge` принимает администратор.

### `BalanceTransfer`

Смысл: перенос остатка между счетами одной или разных единиц.

Поля:

- `from_account`
- `to_account`
- `amount_from`
- `amount_to`
- `conversion_rate`
- `reason`
- `created_by`
- `created_at`

Если перенос идет рубли -> занятия, `amount_from` хранит рубли, `amount_to` хранит рассчитанное количество занятий, `conversion_rate` хранит цену занятия на дату операции.

## Зарплата и расчетные листы

Зарплата должна начисляться при списании, потому что именно списание подтверждает финансовый факт.

### `StaffCompensationRule`

Правило назначает руководитель.

Фактически реализованный первый вариант:

- `staff_member`
- `service`, опционально: пустое значение означает общую ставку специалиста
- `funding_source`, опционально: ставка по источнику финансирования приоритетнее общей
- `rate_type`: per_session, hourly
- `amount`
- `min_duration_minutes`, опционально
- `max_duration_minutes`, опционально
- `starts_on`
- `ends_on`
- `is_active`
- `note`

Правила:

- для обычных услуг зарплата зависит от длительности и наименования услуги;
- для грантов можно завести отдельные правила через `funding_source`;
- если в занятии несколько специалистов, табель считает каждое назначение специалиста;
- начисление в табеле появляется только при решении `списать`;
- если в групповом занятии списаны участники из разных источников финансирования, источниковые/грантовые ставки не применяются без явного общего источника;
- persisted-начисления и утвержденные расчетные листы используют тот же подбор ставки, что и табель.

Отложено:

- `pay_basis=per_charged_participant`;
- `fixed_amount` за период;
- `percent_of_charge`;
- отдельная group policy для начисления по каждому ребенку группы.

### `PayrollAccrual`

Смысл: начисление специалисту, созданное после списания.

Поля:

- `staff_assignment`
- `appointment_participant`, если начисление связано с конкретным участником
- `ledger_entry`
- `staff_member`
- `pay_rule`
- `amount`
- `status`: draft, approved, paid, cancelled
- `created_at`
- `approved_by`
- `approved_at`

Ограничения:

- не создавать повторное начисление на тот же `ledger_entry + staff_assignment`, если правило не допускает несколько строк;
- отмена списания должна создавать корректирующую строку, а не удалять историю.

### `PayrollSheet`

Смысл: расчетный лист специалиста за произвольный период.

Поля:

- `staff_member`
- `date_from`
- `date_to`
- `status`: draft, approved, sent
- `total_amount`
- `created_by`
- `approved_by`

### `PayrollSheetLine`

Поля:

- `payroll_sheet`
- `payroll_accrual`
- `appointment`
- `service`
- `duration_minutes`
- `child`
- `amount`

Экспорт:

- печать;
- копирование текста;
- email;
- мессенджер позже как отдельный канал, не как часть БД.

## Гранты

Грант распределяется от услуги/направления к специалистам, но нужен быстрый сценарий сразу `специалист + количество занятий`.

### `FundingServiceQuota`

Смысл: квота гранта по услуге/направлению.

Фактически реализованный первый вариант:

- `funding_source`
- `service`
- `planned_sessions`
- `starts_on`
- `ends_on`
- `note`

Отложено:

- квота по `service_category` без конкретной услуги;
- жесткое ограничение суммы распределений на уровне формы;
- `pay_mode` на уровне квоты.

### `FundingStaffAllocation`

Смысл: часть грантовой квоты, распределенная на специалиста.

Поля:

- `service_quota`, опционально;
- `funding_source`
- `service`
- `staff_member`
- `allocated_sessions`
- `session_pay_amount`
- `starts_on`
- `ends_on`
- `note`

Правила:

- сумма `allocated_sessions` по специалистам не должна превышать `FundingServiceQuota.planned_sessions`, если квота жесткая;
- смена специалиста в период проекта создается новой строкой с датами, а не перезаписывает историю;
- быстрый сценарий `специалист + количество занятий` создает `FundingStaffAllocation` без `service_quota`.

### Редакции грантового плана

ADR-006 и `docs/58-grant-plan-versioning-contract.md` уточняют жизненный цикл:

- `FundingServiceQuota` и `FundingStaffAllocation` остаются устойчивыми
  корнями и текущими проекциями;
- каждое создание, изменение и закрытие добавляет типизированную
  `FundingServiceQuotaRevision` или `FundingStaffAllocationRevision`;
- интерактивная редакция требует автора-руководителя и отдельное основание;
- бизнес-идентичность корня неизменяема, а смена специалиста выполняется
  закрытием старой и созданием новой позиции;
- старые строки backfill-ятся как `legacy_import` без вымышленного автора;
- физическое удаление корней и истории запрещено;
- `PayrollAccrual` сохраняет ссылку на редакцию грантовой ставки вместе со
  снимком суммы.

### `GrantRecipientAllocation`

Смысл: выделение грантовых занятий получателю.

Поля:

- `funding_source`
- `child`
- `service`
- `allocated_sessions`
- `balance_account`
- `valid_from`
- `valid_until`
- `note`

Реализовано: при создании выделения без выбранного счета система создает `BalanceAccount` в занятиях по выбранному источнику, получателю и услуге. Grant report показывает выделено, списано и остаток по связанному счету. Факт списаний по выделению ограничен датами `valid_from`/`valid_until` и услугой выделения, чтобы один грантовый счет получателя не подтягивал чужие услуги или списания вне периода.

## Финансовая аналитика центра, расходы и оборудование

Пользователь хочет единый контур, поэтому модель должна быть предусмотрена, но внедрять ее лучше после стабилизации расписания, балансов и зарплаты.

### `CenterExpenseCategory`

Примеры:

- хозяйственные расходы;
- коммунальные платежи;
- оборудование;
- инвентарь;
- зарплата административная;
- прочее.

### `CenterExpense`

Поля:

- `category`
- `expense_date`
- `title`
- `quantity`
- `amount`
- `note`
- `created_by`

### `ExpenseFundingSplit`

## Индексы и ограничения

Обязательные индексы:

- `Appointment(starts_at, ends_at, status)`
- `Appointment(room, starts_at, ends_at)`
- `AppointmentParticipant(child, starts_at_snapshot, ends_at_snapshot)`
- `AppointmentParticipant(appointment, child)` unique
- `AppointmentStaffAssignment(staff_member, starts_at_snapshot, ends_at_snapshot)`
- `AppointmentStaffAssignment(appointment, staff_member)` unique
- `RecipientRepresentative(child, is_primary)`
- `RecipientRepresentative(child, receives_schedule)`
- `LedgerEntry(account, created_at)`
- `LedgerEntry(appointment_participant)`
- `PayrollAccrual(staff_member, created_at)`
- `GrantStaffQuota(grant_quota, staff_member)`

PostgreSQL constraints:

- exclusion constraint для пересечений получателя через `AppointmentParticipant` — реализовано в миграции `0011`;
- exclusion constraint для пересечений специалиста через `AppointmentStaffAssignment` — реализовано в миграции `0011`;
- partial unique для одного основного представителя на получателя;
- partial unique для одного подписанта договора на получателя, если это правило подтверждено;
- check constraints для положительных сумм, длительностей и лимитов.

Кабинетная вместимость не укладывается в простой exclusion constraint, потому что зависит от агрегатного количества пересекающихся специалистов и получателей. Ее нужно проверять в доменном сервисе внутри транзакции. Для надежности сервис должен блокировать пересекающиеся строки `Appointment` по кабинету через `select_for_update` на время проверки и создания.

## Безопасный миграционный план

### Шаг 1. Добавить новые таблицы без удаления старых полей

- `RecipientRepresentative`
- `AppointmentParticipant`
- `AppointmentStaffAssignment`
- `AppointmentRoomOverride`
- новые поля `Room`
- зарплатные и грантовые таблицы можно добавить позже, после стабилизации расписания

Проверка:

- старый UI продолжает работать;
- миграция обратима;
- существующие занятия не потеряны.

### Шаг 2. Backfill текущих данных

Для каждого старого `Appointment`:

- создать `AppointmentParticipant` из `appointment.child`;
- создать `AppointmentStaffAssignment` из `appointment.staff_member`;
- перенести `attendance_status`, `billing_decision`, `billing_account`, `sequence_number` в участника;
- заполнить snapshot-время.

Для каждого `Child.primary_parent`:

- создать `RecipientRepresentative(is_primary=true, signs_contract=true, receives_schedule=true)`.

Проверка:

- количество участников равно количеству старых занятий;
- количество назначений специалистов равно количеству старых занятий;
- балансы и табели дают прежние результаты на старых данных.

### Шаг 3. Переключить сервисы расписания

- проверка конфликтов получателя идет через `AppointmentParticipant`;
- проверка конфликтов специалиста идет через `AppointmentStaffAssignment`;
- проверка кабинета использует новые правила `Room`;
- текущий PostgreSQL constraint `no_room_overlap_active_appointments` должен быть удален или заменен, иначе вместимость больше 1 не заработает.

Проверка:

- индивидуальное занятие блокирует специалиста;
- групповое занятие позволяет добавить детей до лимита;
- кабинет с лимитом 2 специалистов допускает две параллельные сессии;
- кабинет с лимитом 1 специалист предупреждает и требует override.

### Шаг 4. Переключить UI создания занятия

Новый мастер:

1. тип занятия: индивидуальное или групповое;
2. услуга;
3. время;
4. кабинет;
5. специалисты;
6. получатели;
7. счета списания;
8. проверка конфликтов и лимитов;
9. подтверждение или hold-to-override.

Проверка:

- администратор может создать индивидуальное занятие за минимальное число кликов;
- администратор может создать групповое занятие и добавить нескольких детей;
- предупреждения понятны и не теряются после ошибки формы.

### Шаг 5. Переключить списания

- `LedgerEntry` начинает ссылаться на `AppointmentParticipant`;
- старые списания по `Appointment` остаются читаемыми;
- новые списания создают основу для `PayrollAccrual`.

Проверка:

- в группе можно списать одного ребенка и не списать другого;
- отмена списания создает корректировку;
- остаток счета считается из ledger.

### Шаг 6. Добавить зарплату

- `StaffCompensationRule` — реализовано;
- расчет начислений в табеле по `AppointmentStaffAssignment` — реализовано;
- `PayrollAccrual` — реализовано;
- `PayrollSheet` — реализовано;
- `PayrollSheetLine` — реализовано.

Проверка:

- начисление появляется только после решения `списать`;
- руководитель может задать разные правила для обычных услуг и грантов;
- расчетный лист формируется за произвольный период.

### Шаг 7. Добавить грантовые квоты

- `FundingServiceQuota` — реализовано;
- `FundingStaffAllocation` — реализовано;
- отображение квот в grant report — реализовано;
- `GrantRecipientAllocation` — реализовано;
- отдельный мастер быстрого сценария создания квоты и распределения по специалисту — реализован.

Проверка:

- грант задается по услуге/направлению;
- квота распределяется между специалистами;
- быстрый сценарий `специалист + количество занятий` работает;
- смена специалиста по непересекающимся периодам корректно отражается в
  текущем отчете; append-only история изменения плана остается отдельным
  опасным срезом БД.

### Шаг 8. Расходы, оборудование, договоры

После стабилизации расписания, списаний, зарплат и грантов:

- хозяйственные расходы;
- коммунальные платежи;
- оборудование;
- договоры пожертвования;
- договоры с получателями услуг;
- донорская отчетность.

## Что нельзя делать параллельно

- Нельзя двум агентам одновременно менять `operations/models.py`.
- Нельзя двум агентам одновременно создавать миграции.
- Нельзя сначала делать UI групповых занятий без утвержденной модели `AppointmentParticipant` и `AppointmentStaffAssignment`.
- Нельзя импортировать Excel до миграции представителей и новой модели занятий.
- Нельзя удалять старые поля `Appointment.child` и `Appointment.staff_member` до полного backfill и переключения отчетов.

## Рекомендуемый первый вертикальный срез

Первый срез должен быть только про новую модель занятия и кабинетные лимиты.

Состав:

1. Новые таблицы `AppointmentParticipant`, `AppointmentStaffAssignment`, `RecipientRepresentative`.
2. Новые поля кабинета для лимитов специалистов и получателей.
3. Backfill старых данных.
4. Переписанная проверка конфликтов.
5. Минимальный UI создания группового занятия.
6. Тесты:
   - индивидуальное занятие блокирует специалиста;
   - групповая сессия принимает нескольких получателей;
   - один получатель не попадает в два занятия одновременно;
   - два специалиста могут работать в большом зале, если лимит разрешает;
   - override кабинета требует причину;
   - представитель с `receives_schedule=true` попадает в список рассылки.

Только после этого безопасно переходить к зарплате, грантовым квотам и финансовой аналитике.

## Дополнение 2026-06-24: инвариант списания участника

- Участник занятия (`AppointmentParticipant`) не может иметь решение `CHARGE` без счета баланса.
- Счетчик `ProgramBlock.paid_count` считается по участникам с `CHARGE` и непустым `billing_account`, чтобы каскады не считали неполные старые записи как оплаченные.
- Табель и начисления зарплаты должны начислять оплату только по факту корректного списания со счета, а не по одному строковому статусу.
- Лимит бронирования в мастере каскада также считает `CHARGE` без счета неоплаченной бронью, пока запись не приведена к корректному финансовому состоянию.
- Проводка `LedgerEntry` для группового занятия валидируется по `appointment_participant.child`; legacy-проверка `appointment.child == account.child` применяется только к проводкам без строки участника.
- `billing.apply_decision()` должен валидировать счет до записи `billing_decision/billing_account` на `Appointment`, чтобы неверный счет другого получателя не попадал даже в промежуточное состояние.
- Подтверждения, публичный экран ответа и рабочие заголовки карточки, редактирования, переноса и отмены не должны пересобирать текст из legacy `Appointment.child/staff_member`: для группы используются `AppointmentParticipant` и `AppointmentStaffAssignment`, а отправляемое письмо берет сохраненный `AppointmentConfirmation.message`.
- Массовая отмена/перенос по специалисту должен искать занятия через `AppointmentStaffAssignment`, а уведомления представителям создавать по участникам группы и `RecipientRepresentative.receives_schedule`, с fallback на `primary_parent` только для старых записей без связей представителей. Дедупликация по одному представителю недопустима, если этот представитель получает расписание для нескольких участников одной группы.
- Предложения новых окон при массовой отмене/переносе должны проверять конфликты всех `AppointmentParticipant`, а не только legacy `Appointment.child`.
- Подсказки переноса, ручного сдвига и форма переноса должны исключать исходное время занятия целиком, а не только пару `starts_at + legacy staff_member`, иначе групповое занятие с ассистентом может получить ложный вариант переноса на то же время.
- Рабочая очередь администратора должна показывать snapshot-участников и назначенных специалистов в задачах списаний, отметки посещения, переноса и email-согласований, чтобы администратор видел, по чьему расписанию ожидается действие.
- Экран "Завтра" должен использовать `AppointmentParticipant` как основной источник имени получателя и `AppointmentStaffAssignment` как основной источник специалиста, если snapshot-строки уже есть.
- Карточка получателя должна показывать назначенных специалистов через `AppointmentStaffAssignment`, если назначения уже есть; legacy `Appointment.staff_member` остается fallback.
- API календаря должен формировать пользовательский заголовок и цветовые метки из `AppointmentParticipant`/`AppointmentStaffAssignment`, если snapshot-строки уже есть; legacy-поля остаются только fallback для старых записей.
- При будущей миграции на DB-level constraint этот инвариант нужно backfill-проверить: найти `AppointmentParticipant` со `billing_decision='charge'` и `billing_account_id IS NULL`, затем либо привязать счет, либо перевести решение в `undecided`.
