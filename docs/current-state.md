# Текущее состояние проекта "Радость моя"

Дата среза: 2026-06-23

Этот документ нужен как точка входа для следующего чата или следующего агента. После нового интервью появились серьезные уточнения, поэтому дальнейшие изменения нельзя делать хаотично: сначала нужно сверить требования, доменную модель, БД, UX-сценарии и только потом писать код.

## Цель продукта

Система должна стать рабочей операционной CRM/МИС для реабилитационного центра: расписание, получатели, представители, специалисты, кабинеты, программы занятий, оплаты, гранты/фонды/спонсоры, табели, согласования и ежедневная работа администратора.

Текущая цель уже не "быстрый MVP". Нужен серьезный, удобный и долговечный продукт, который можно использовать каждый день администратору и руководителю без высокой компьютерной квалификации.

## Текущий стек

- Backend: Django 5, server-rendered templates, Django ORM.
- UI: HTML templates, Bootstrap, FullCalendar, vanilla JavaScript.
- Database: PostgreSQL в production, локально может использоваться SQLite/PostgreSQL в зависимости от окружения.
- Background/infra: Redis, Docker Compose, Caddy, Gunicorn.
- Deployment: VPS, путь проекта на сервере `/opt/rm`.
- Временный production URL: `https://rm.147-45-102-93.sslip.io/`.
- GitHub remote: `Gordey-ap01/rm.git`.

Текущий стек остается прагматичным для этой задачи: Django подходит для сложной доменной модели, админки, ролей, форм, миграций и быстрого развития. React можно добавить точечно для сложного календаря/планировщика, но переписывать весь продукт на React сейчас рискованно: проблема проекта не в отсутствии React, а в необходимости уточнить бизнес-правила, БД и UX-потоки.

## Production и доступ

- Приложение поднято на VPS через Docker Compose.
- Caddy слушает 80/443 и проксирует web-контейнер.
- На уровне VPS и панели провайдера должны быть открыты входящие TCP 22/80/443.
- Для исходящего трафика нужны как минимум TCP 80/443 и DNS: TCP/UDP 53.
- Ошибка с недоступностью сайта была связана с конфликтом firewall-групп у провайдера, а не с Django.
- Root-доступ по SSH был отключен для безопасности; консоль провайдера остается отдельным аварийным доступом.
- Пароли и секреты нельзя фиксировать в документах и коммитах.

Для долгой эксплуатации желателен нормальный домен, например `crm.<домен-центра>`, но временный `sslip.io` может жить для переходного периода, если центр принимает риск зависимости от временного домена.

## Что уже реализовано

### Базовые справочники и роли

- Получатели и представители.
- Специалисты.
- Услуги.
- Кабинеты/помещения.
- Пользователи и разграничение через Django auth.
- Специалистский кабинет с мобильным сценарием.

### Расписание

- Календарь занятий.
- Дневной вид "по специалистам" со столбцами специалистов.
- Создание и редактирование занятий.
- Статусы занятия: черновик/предложено/бронь/подтверждено/проведено/отменено/неявка/перенесено.
- Проверка конфликтов по получателю, специалисту и кабинету.
- Учет рабочего времени специалиста.
- Учет отпуска/отгула/заявки отсутствия.
- Возможность осознанно подтвердить выход специалиста вне графика через hold-to-confirm.
- Перенос и отмена занятия с решением по списанию.

### Программы, каскады и серии

- Программа занятий после консультации.
- Блоки/каскады программы.
- Нумерация занятий внутри блока.
- Мастер подбора окон для блока программы.
- Создание серии занятий из предложенных окон.
- Бронь сверх доступной оплаты как отдельный осознанный режим.
- Миграция средств между блоками/счетами в базовом виде.

### Финансы и балансы

- Счета баланса в занятиях или рублях.
- Источник финансирования: личные средства, грант, фонд, спонсор и другие варианты.
- Журнал операций `LedgerEntry`, чтобы остаток считался из истории, а не из одного ручного поля.
- Платежи.
- Цветовые метки счетов.
- Предупреждения о низких остатках в базовом виде.
- Списание только после явного решения администратора.

### Согласования и рассылки

- Модель подтверждения занятия.
- Отправка email-согласования специалисту, представителю или получателю.
- Публичная ссылка подтвердить/отклонить.
- Очередь задач по ожидающим/отклоненным/ошибочным подтверждениям.

SMTP для реальной промышленной рассылки еще не закреплен как настроенный эксплуатационный контур. Это отдельная задача после согласования домена/почтового провайдера.

### Документы, рекомендации и отчеты

- Рекомендации после консультации.
- Документы и согласия в базовой модели.
- Табель специалиста за период.
- Отчеты по источникам финансирования в базовом виде.
- Ежедневная рабочая очередь администратора.

### UX/UI

- Общий стиль был сдвинут в сторону логотипа: цветность, стеклянность, мягкие панели.
- В админских и рабочих экранах есть попытка совместить glassmorphism с более плотной операционной UI.
- Добавлены глобальные searchable select controls: выпадающие списки можно открыть и начать печатать для поиска.
- По референсам медицинских систем появилась важная UX-идея: дневной календарь должен быть главным рабочим экраном администратора, с колонками по специалистам/кабинетам и цветными событиями.

## Критические пробелы после нового интервью

Следующий этап должен начаться не с кода, а с анализа интервью и проектирования.

1. Термины нужно зафиксировать заново: получатель, представитель, программа, каскад, блок, серия, счет, бронь, оплата, миграция средств, фонд, спонсор, согласование, табель.
2. БД может потребовать серьезных изменений. Особенно опасны финансы, программы занятий, кабинеты с несколькими специалистами, емкость кабинета и правила переноса.
3. Нужна полная карта сценариев администратора на день: запись, перенос, отмена, оплата, согласование, свободные окна, замены, списание.
4. Нужна отдельная карта сценариев руководителя: остатки денег/занятий, фонды, сроки освоения, табели, контроль ошибок.
5. Нужна отдельная карта сценариев специалиста с телефона: расписание, отметка занятия, заметка, график, отпуск/отгул.
6. Нужны точные правила для кабинетов: когда несколько специалистов могут быть в одном кабинете, что значит вместимость, какие услуги требуют отдельный кабинет.
7. Нужно уточнить модель оплаты: оплата за занятие, за каскад, произвольная сумма на баланс, перенос остатка между каскадами и автоматический пересчет количества занятий.
8. Нужно уточнить правила отмены день-в-день: когда списывать, когда не списывать, когда предлагать сдвиг расписания, когда согласовывать с представителем.
9. Нужно решить, как система предлагает окна: сначала специалист, потом представитель, или наоборот; где администратор утверждает финальное решение.
10. Нужно продумать audit/history: кто изменил занятие, оплату, статус, график специалиста, перенос денег.
11. Нужно подготовить импорт из Excel, но только после стабилизации модели данных.
12. Нужно продолжить production-hardening: нормальный домен, SMTP, внешние бэкапы, мониторинг, политика доступа.

## Рекомендуемый порядок следующей работы

### Фаза 1. Разбор интервью и требований

- Прочитать `docs/current-state.md`.
- Прочитать новое интервью полностью.
- Выписать все новые требования отдельным списком.
- Отделить факты от предположений.
- Составить список противоречий и вопросов к руководителю.
- Обновить PRD и доменный словарь.

### Фаза 2. Ревизия модели данных

- Сравнить требования с текущими моделями Django.
- Выявить, какие сущности нужно добавить, разделить или переименовать.
- Отдельно проверить финансы, программы/каскады, кабинеты, доступность специалистов, историю изменений.
- Написать миграционный план до правок.
- Не делать несколько конкурирующих миграций параллельно.

### Фаза 3. UX/UI рабочих сценариев

- Спроектировать главный экран администратора: календарь по специалистам/кабинетам, фильтры, действия из события, быстрый поиск.
- Спроектировать сценарий записи/переноса/отмены за минимальное число кликов.
- Спроектировать мастер серии занятий и согласования.
- Спроектировать финансовый экран получателя и счетов.
- Отдельно проверить мобильный кабинет специалиста.

### Фаза 4. Реализация вертикальными срезами

Каждая задача должна проходить через БД, валидацию, UI и тесты. Нельзя отдельно "накидать UI", если под ним не согласована модель данных.

Пример порядка:

1. Кабинеты и емкость кабинета.
2. Рабочее время специалиста и override вне графика.
3. Мастер серии занятий с корректным учетом кабинета/специалиста/получателя.
4. Финансовые счета и блокировки при недостатке средств.
5. Перенос/миграция средств между каскадами.
6. Согласование с представителем/получателем.
7. Табель и отчеты руководителя.
8. Импорт Excel после стабилизации модели.

## Нужно ли несколько агентов

Сразу несколько агентов сейчас опасны, если они начнут одновременно менять модели, миграции и общие шаблоны. Правильнее сначала один ведущий агент должен сделать синтез интервью, обновить PRD, доменную модель и план работ.

После утверждения общей схемы можно подключать несколько агентов:

- Агент 1: доменная модель, миграции, тесты бизнес-правил.
- Агент 2: UX/UI календаря, формы, рабочие экраны администратора.
- Агент 3: финансы, счета, отчеты, табель.
- Агент 4: production, безопасность, SMTP, бэкапы, мониторинг.

Правило координации: один владелец миграций БД. Остальные агенты не меняют модели и миграции без согласованного контракта.

## Что не делать дальше

- Не начинать "быстро править экран" до разбора интервью, если правка затрагивает БД или бизнес-логику.
- Не смешивать несколько крупных изменений в одном коммите.
- Не переписывать проект на React только ради ощущения современности.
- Не переносить реальные Excel-данные до ревизии модели.
- Не хранить пароли, токены, персональные данные и production-секреты в markdown-документах.
- Не давать нескольким агентам одновременно менять `operations/models.py` и миграции.
