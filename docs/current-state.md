## Новый срез 61D-5: локальная приемка

- Пауза/возобновление программы имеют отдельные команды и неизменяемый журнал.
  Пауза доступна администратору/руководителю; возобновление — руководителю.
  Принятый UUID распознается до stale/status-проверок; история руководителя
  имеет приоритет. Старые paused-программы не получают вымышленный backfill.
- Пауза не переписывает расписание и финансовые факты. Новые назначения
  проверяют программу под блокировкой; обычные заметки и учет проведенного
  занятия остаются доступны. Возобновление само не создает занятия.
- Исправлена конкурентная перезапись привязки участника старой формой:
  сохранение считывает актуального участника под блокировкой, проверяет
  текущий и выбранный каскады; при отсутствии изменений запись не выполняется.
- Новые блокировки выявили race повторного UUID при создании/join серии:
  повтор мог завершиться ValidationError на full_clean до INSERT. Теперь
  обработчик проверяет уже принятый UUID и его исходные данные; при отсутствии
  такого ключа исходная ошибка остается ошибкой. Оба прежних PG-теста
  одновременного создания прошли после исправления; повторное ревью прошло.
- Чистая PostgreSQL-цепочка `0001-0067` прошла. Restricted runtime-role
  выполнила обе команды, а UPDATE/DELETE нового журнала были запрещены.
- Независимое ревью после исправления замечания прошло. Browser QA:
  admin pause, director resume, приоритет, stale 409, replay без нового события,
  история; Chrome 390px без переполнения и console errors. Обратная ссылка
  «К получателю» проверена; новый переход из карточки получателя отдельно
  в браузере не проверялся. Все данные синтетические.
- Новый модуль: PostgreSQL 18 passed за 22.546s; SQLite 15 passed и 3
  PostgreSQL-only skips. Включены raw SQL/deferred guards, migration round-trip,
  preflight и запрет reverse после истории; гонка подтверждает ожидание
  писателя через `pg_blocking_pids`, затем отказ назначения после паузы.
- Старые серии/реестр/состав/stop-resume: 192 passed, 4 failed в первом прогоне
  за 432.40s. Две проверки UUID исправлены в коде, две старые проверки
  адаптированы к новому запрету пустой серии и перечитыванию состояния.
  Все четыре прошли отдельно: UUID 2 passed за 36.42s; остальные 2 passed
  за 2.114s. Ruff, Django check, migration dry-run, manifests и diff-check чистые.
- Общий CI еще ожидается. Логи этого среза:
  `.runtime/program-lifecycle-regression.log`, `.runtime/program-lifecycle-uuid-race.log`,
  `.runtime/program_acl_probe.log`.
  Разбор первого общего CI — `.runtime/program-lifecycle-ci-failed.log`;
  последовательность миграционных/PG-тестов — `.runtime/program-lifecycle-order-fixed.log`.

## Принятый результат: 61D-4

Код `103cf8b`; [CI 34292476098](https://github.com/Gordey-ap01/rm/actions/runs/34292476098)
прошел: `1114 passed, 490 warnings` за `841.77s`. Весь job — 22 минуты
30 секунд, backup/restore drill — 7 минут 14 секунд.

- Администратор/руководитель останавливает новые запуски из карточки серии.
  Возобновление доступно только руководителю после последнего явного STOP.
  Отмена занятий и снятие участия не считаются временной остановкой.
- Действие требует основания, UUID и ожидаемого последнего события.
  Повтор принятого UUID не пишет второе событие, даже после позднейших решений.
  Устаревшая форма получает 409; приоритет руководителя сохраняется.
- Сервис, модель и PostgreSQL guard `0066` проверяют один и тот же
  непосредственный STOP-предшественник. Миграционный preflight блокирует
  некорректную старую историю, ничего в ней не исправляя автоматически.
- Остановка прерывает незавершенные запуски. Возобновление разрешает новые
  запуски, но не создает занятия само по себе. Занятия, участия, назначения
  специалистов и финансовые факты сохраняются.
- Карточка, история и реестр различают остановленные и отмененные серии.
  Отмененные legacy-серии без журнала остаются в фильтре «Отменена».

## Окружение и восстановление

Docker Desktop восстановлен после зависших socket-файлов. Только локальные
runtime-каталоги переименованы с сохранением копий; базы, тома и настройки
не сбрасывались. Остальные контейнеры пользователя сохранены и работают.
Не останавливать весь Docker ради очистки тестовой БД.

При обрыве: git status → текущий commit/run CI → верх этого файла →
профильный контракт. Локальные логи 61D-4 — `.runtime/stop-resume-*.log`;
они игнорируются Git. Принятый checkpoint и результат CI должны быть в Git,
чтобы продолжение не зависело от одной локальной сессии.

## Правила сохранности

- Один владелец `operations/models.py` и migration chain; остальные агенты
  работают в непересекающихся файлах. Финансы/расписание/полномочия закрываются
  целым сценарием: правило, сервис, UI, аудит, проверки, документация.
- Не запускать production backfill/import apply без preflight.
- `0048` не откатывается через `migrate 0047`. После новой истории
  нельзя откатывать `0053` (снимки), `0054` (сдачи/private),
  `0055/0056` (групповой состав/join), `0058/0059` (native revision/run/result),
  `0060` (cross-revision results), `0061` (retry targets),
  `0062` (stop/resume decisions), `0063` (cancel results), `0064` (withdraw/lineage),
  `0065` (операторские решения). Откат приложения сохраняет аддитивную
  схему, immutable-историю и private volume.
- Reverse `0066` проверен для миграционного round-trip, но ослабляет guard;
  production rollback не должен обходить новое доменное ограничение.
- Не включать SMTP как надежную доставку до transactional outbox/claim.
- Не объединять runtime/migration DB-роли и не давать runtime DDL,
  отключение triggers или замену защитных функций.
- Не хранить ключи, пароли, production-конфиги и реальные ПДн в Git.
- SQLite не доказывает PostgreSQL concurrency. Не повторять принятые
  проверки без новых изменений, failures или конкретного нерешенного риска.
- Не возвращаться к очередным микросрезам документов/сертификатов без
  продуктового приоритета PRD.
