# 75. Согласуемое изменение постоянного графика специалиста

Реализовано 16 сентября, установлено 17 сентября 2026 года.

## Поведение

В кабинете специалиста есть «Запросить изменение графика» и список заявок.
В шапке показываются количества ожидающих, согласованных, отклонённых заявок
и решений на контроле руководителя. Администратор и руководитель могут
создать заявку за любого активного специалиста от своего имени.

Форма содержит дату начала (не ранее завтрашнего дня), основание и все семь
дней недели. Каждый день явно выходной либо содержит один или несколько
непересекающихся интервалов. Исходная форма берёт действующий на завтра график.
Интервалы добавляются компактно; ошибки сохраняют введённые значения.

Администратор согласует заявку с указанной даты; решение сразу определяет
доступность с этой даты и поступает на контроль руководителю. Руководитель
подтверждает либо отклоняет его. Повторное согласование уже согласованной
заявки отклоняется с объяснением; для другой недельной сетки нужна новая заявка.
Решение руководителя может изменить только руководитель. Основание обязательно,
автор и роль сохраняются в истории. Отключённый мобильный кабинет запрещает
специалисту создавать и просматривать заявки; оператор действует со своими правами.

Очередь `/work-queue/#queue-staff-schedules` показывает новые заявки и решения
для контроля. Счётчик отражает все записи, в очереди первые 40; полный список
постраничный (25). Карточка показывает предложенный график, затронутые будущие
занятия, решения и даты утверждённых версий. Никакое занятие, состав группы,
посещаемость или финансовый факт не переносится и не изменяется автоматически.

## Хранение и защита истории

Аддитивная миграция `0071_staff_schedule_revisions` добавляет три модели:
`StaffScheduleChangeRequest`, `StaffScheduleChangeDecision`, `StaffScheduleRevision`.
Неделя хранится строгим семидневным JSON-снимком вместо пяти предложенных ранее
таблиц: сервис проверяет состав, выходные, формат и непересечение интервалов
в одной транзакции. Это уменьшает сложность атомарного создания снимка.

Сервис `operations/services/staff_schedules.py` предоставляет `create_request`,
`decide_request`, `effective_windows`, `impact_rows`, `latest_revision_id`.
Последнее имя оставлено в API как токен версии: это максимальный ID решения
по всем заявкам специалиста, а не ID применяемой недельной версии. Поэтому
даже отмена будущей версии делает ранее открытые формы устаревшими.

Сначала блокируется StaffMember, затем заявка; так решения по разным заявкам
одного человека сериализованы. Уникальные ограничения БД обеспечивают одно
текущее решение и одну текущую версию на дату. UUID + SHA-256 payload дают
идемпотентный повтор; другой payload с тем же ключом отклоняется. Ожидаемые
ID решения и токен графика защищают от устаревших форм. История решений
дополняется, ссылки PROTECT препятствуют удалению заявки с историей.

Дата не может быть сегодняшней: это сознательное уточнение первоначального
предложения, чтобы не менять уже прошедшую часть рабочего дня. Поздняя отмена
сохраняет ранее действовавший период и добавляет восстановленную версию
с завтрашнего дня. Если предшественника нет, замораживается снимок старых окон
с fallback 09:00–18:00. Более новая утверждённая версия не отменяется чужим
старым решением; конфликт возвращается пользователю.

## Интеграция доступности

`staff_unavailability_reason` — единая проверка: согласованное отсутствие
имеет приоритет, затем применяется последняя действующая версия графика.
До первой версии остаются прежние StaffAvailability и fallback 09:00–18:00.
Выходной в новой версии — действительно закрытый день, а не fallback.

Поиск свободных окон, предложения переноса и создание планов используют
общий `iter_available_slot_times`, включая ранние/вечерние интервалы и всех
специалистов группы. Явные границы поиска сохраняются. После появления
утверждённой версии старые быстрые изменения StaffAvailability в кабинете
блокируются под той же StaffMember-блокировкой; интерфейс направляет к заявке.
Больничные/отпуска, конкретные занятия и рассылка остаются отдельными процессами.
