# ADR-003: полномочия и ручное решение ожидающих запросов

## Статус

Accepted

## Дата

2026-07-24

## Контекст

В системе уже есть несколько независимых процессов согласования:

- подтверждение занятия специалистом, представителем или получателем;
- согласование шага переноса;
- заявка специалиста на отсутствие;
- утверждение расчетного листа;
- будущие утверждения расходов, грантовых изменений и массовых импортов.

Сейчас права в основном сведены к `user.is_staff`, а ответ хранится прямо в
целевой сущности. Такая модель не различает руководителя и администратора,
не показывает источник ручного решения и затрудняет безопасное
переопределение решения.

Ожидание ответа сотрудника не должно останавливать работу центра. При этом
ручное решение нельзя записывать так, будто его принял сам адресат.

## Решение

### Роли полномочий

- `director`: суперпользователь или пользователь группы `Руководители`;
- `administrator`: staff-пользователь или пользователь группы
  `Администраторы`;
- `specialist`: пользователь, связанный со `StaffMember`, без управленческих
  полномочий;
- директор включает оперативные полномочия администратора.

### Приоритет

- руководитель может решить любой ожидающий запрос;
- администратор может решить любой оперативный запрос;
- в управленческой области администратор может принять экстренное эффективное
  решение, которое требует последующего контроля руководителя;
- руководитель может переопределить решение администратора;
- администратор не может переопределить окончательное решение руководителя.

### История решений

Для согласований используется append-only запись решения:

- целевой запрос;
- решение `confirm/decline`;
- источник: адресат, администратор или руководитель;
- пользователь, роль на момент решения, время и основание;
- ссылка на предыдущее решение;
- признак текущего решения.

Целевая сущность может хранить текущий статус как денормализованную сводку, но
источником истории является журнал решений.

### Этапность

1. Первый вертикальный срез - ручное решение `AppointmentConfirmation`.
2. Второй срез - заявки специалистов с приоритетом руководителя.
3. После двух проверенных процессов решить, нужен ли общий
   `WorkflowDecisionRequest`, либо безопаснее оставить типизированные журналы.
4. Финансовые, payroll, grant и import решения подключаются только отдельными
   вертикальными срезами.

Оба первых типизированных среза реализованы миграциями `0044` и `0045`.
Решение об общем workflow engine должно приниматься отдельным ADR после
сравнения их фактических различий, а не автоматически.

## Альтернативы

### Только менять `status` и `responded_by`

Отклонено: теряется надежная история переопределений, а ручной ответ легко
принять за ответ адресата.

### Сразу создать универсальный workflow engine

Отклонено для первого среза: слишком большой риск построить абстракцию до
проверки реальных процессов расписания и кадровых заявок.

### Запретить администратору решать управленческие запросы

Отклонено: отсутствие руководителя не должно останавливать ежедневную работу.
Вместо запрета используется эффективное экстренное решение с последующим
контролем.

## Последствия

- права становятся явными и тестируемыми;
- ручное решение не фальсифицирует ответ специалиста или представителя;
- история переопределений не удаляется;
- пользователя, зафиксированного как автор ручного решения, нельзя физически
  удалить; доступ закрывается деактивацией пользователя;
- первый срез требует additive-миграцию;
- старые подтверждения продолжают работать через текущий статус;
- финансовые и расписательные эффекты остаются в существующих доменных
  сервисах и не переносятся в слой полномочий.
