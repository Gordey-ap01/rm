# ADR-009: редакции серий и append-only запуски материализации

## Статус

Accepted

## Дата

2026-08-28

## Контекст

`AppointmentSeries` одновременно хранит идентичность серии, текущие параметры
расписания и legacy-проекцию состава. Нормализованный состав 61A также привязан
непосредственно к серии, а `AppointmentSeriesOccurrence` является неизменяемым
результатом одной даты. Этого достаточно для первого создания и операции
join-existing, но недостаточно для безопасного редактирования будущего состава
и повторной обработки пропущенной даты.

Обновление текущих строк на месте уничтожило бы объяснимость уже созданных
занятий. Разрешение `UPDATE` существующего occurrence уничтожило бы причину
предыдущего пропуска. Использование generic auditlog не задает доменных
ограничений, идемпотентности и связи результата с точным составом.

## Решение

- Сохранить `AppointmentSeries` как устойчивый корень и текущую совместимую
  проекцию. Nullable-указатель `current_revision` остается технически
  необходимым для создания корня перед первой редакцией и проверяется
  integrity preflight.
- Добавить типизированный append-only `AppointmentSeriesRevision` с полным
  снимком параметров и отдельными снимками получателей/специалистов.
- Корень хранит `PROTECT`-ссылку `current_revision`. Новая редакция создается
  под row lock с `expected_revision_id`, затем в той же транзакции обновляется
  текущая проекция.
- Уже созданные занятия и их состав не синхронизируются из новой редакции.
  Редактор влияет только на еще не материализованные даты начиная с
  `effective_from`.
- Добавить append-only `AppointmentSeriesMaterializationRun`. Каждый запуск
  хранит режим, диапазон, идемпотентный ключ, fingerprint, автора, роль и
  основание.
- Состояние исполнения run хранить отдельными append-only событиями. Сам
  запрос запуска после принятия не изменяется; аварийно незавершенная операция
  может продолжаться только с тем же ключом и fingerprint.
- Новый `AppointmentSeriesMaterializationResult` является канонической
  append-only историей результатов: ссылается на точные серию, редакцию и
  запуск и образует нумерованную цепочку попыток. Повтор пропуска добавляет
  новый факт, а не изменяет старый.
- Набор дат принятого `retry_skipped` хранится не вычисляемым JSON, а
  нормализованными append-only `AppointmentSeriesRetryTarget`. Каждая цель
  фиксирует текущую вершину цепочки и первый эффективный не-`unchanged` исход
  `skipped`; вершина резервируется для результата этого run. Это сохраняет
  идемпотентное возобновление при сбое и не допускает конкурентного ответвления
  истории.
- Fingerprint `retry_skipped` включает нормализованное основание и точные
  `(scheduled_starts_at, chain_head_result_id, effective_skipped_result_id)`.
  Существующий ключ разрешается до проверки изменяемого статуса и указателя
  текущей редакции; новая операция принимается только для активного корня с
  целостной текущей проекцией, но исполняет immutable-редакцию, применимую ко
  всему выбранному диапазону `create_appointments`. Один run не пересекает
  границу следующей редакции.
- Исполнение retry не создает второй compatibility occurrence: общий
  materializer создает Appointment и новый `created` result либо только новый
  `skipped` result. Appointment успеха обязан совпадать с серией, временем,
  услугой и типом frozen target. Каждая дата коммитится отдельно, а
  `interrupted/resumed/completed` сохраняют проверяемые счетчики.
- Принятый незавершенный retry имеет приоритет над новым `missing_only`; другой
  retry не может продолжить зарезервированную вершину. Это правило одинаково
  проверяется сервисом на SQLite и сервисом плюс triggers на PostgreSQL.
- Revision/result явно маркируют происхождение. Legacy-снимок описывает данные
  на момент миграции; историческая точность результата считается
  реконструированной только после сверки с фактическим составом Appointment,
  иначе остается `legacy_unknown`.
- Существующий `AppointmentSeriesOccurrence` не изменяется миграцией и остается
  совместимой проекцией первой попытки 61A-61B. Backfill копирует его факт в
  result-таблицу через nullable one-to-one `compatibility_occurrence`; native
  dual-write использует ту же связь. PostgreSQL immutable-trigger occurrence на
  время миграции не отключается.
- Один общий materializer читает нормализованный снимок редакции и обслуживает
  индивидуальные и групповые серии. Старые entry points временно остаются
  совместимыми оболочками.
- Appointment/participant, compatibility occurrence и canonical result одной
  даты записываются в одной транзакции. Run создается отдельно и остается
  видимым как незавершенный после аварии; повтор тем же ключом безопасно
  дописывает только отсутствующие атомарные результаты.
- Одноучастниковая legacy-группа допустима только как сохраненный исторический
  снимок для идемпотентного чтения уже покрытых дат. Она не материализует новые
  групповые занятия до будущей редакции с валидным составом.
- Отмена имеет явные режимы: остановить новые запуски либо дополнительно
  отменить будущие неначавшиеся занятия через существующий доменный write-path.
  Join-серия никогда не отменяет общий слот: для нее отдельная команда меняет
  только созданные ею участия. Create-серия не отменяет общий слот, если к нему
  уже присоединены участники других серий.
- Cancel и charge сериализуются на одинаковых строках. Отмена не удаляет и не
  отвязывает ledger; billing не может списать уже отмененное участие.
- Редакции, запуски и результаты защищаются от `UPDATE/DELETE` методами модели
  и PostgreSQL-триггерами. Cross-table принадлежность защищается ограничениями
  или PostgreSQL-триггерами там, где обычный `CHECK` недостаточен.
- Связь occurrence/result с историческим Appointment защищается `PROTECT` на
  обоих поддерживаемых СУБД; техническое удаление не обнуляет provenance.
- Внедрение выполняется отдельными production gates: expand release -> deploy
  dual-write на все writer-процессы -> блокируемый и сверяемый backfill release
  -> trigger/read-switch release. Legacy-поля не удаляются в 61C.
- Исторический run, принятый до появления следующей редакции, может содержать
  результаты будущих дат старого состава: эти факты не переписываются. После
  создания successor ни один новый run старой редакции не может пересекать ее
  `effective_from`; это намеренная асимметрия temporal-контракта.
- Ограниченная production runtime-роль имеет только `SELECT/INSERT` на
  append-only таблицы revision/run/result; PostgreSQL triggers являются вторым
  независимым барьером против `UPDATE/DELETE`.

## Альтернативы

### Изменять серию и состав на месте

Отклонено: невозможно доказать, по какому составу было создано историческое
занятие, а конкурентное редактирование дает silent lost update.

### Представлять каждую редакцию новой строкой `AppointmentSeries`

Отклонено: смешиваются устойчивый идентификатор серии и версия, усложняются
ссылки из программы/расписания и появляется риск повторной материализации одной
даты разными корнями.

### Хранить только JSON-снимок

Отклонено: теряются FK-защита каскадов, счетов и специалистов, нормальные
индексы и проверяемые ограничения состава.

### Использовать только технический auditlog

Отклонено: он не является контрактом materialization, не обеспечивает
идемпотентность запуска и не защищает неизменяемость на уровне PostgreSQL.

## Последствия

- Схема становится больше, но текущие read/write-path сохраняются на период
  совместимого перехода.
- Все рабочие изменения серии и materialization должны проходить через один
  сервис; прямой `ModelForm.save()` остается запрещенным.
- Нужны отдельные migration tests для legacy backfill, reverse guard и
  PostgreSQL-триггеров, а также гонки редактирования/повтора.
- Lock-order для materialization/cancel является частью доменного контракта, а
  не деталью конкретной функции.
- Смена услуги, режима и правила повторения выполняется новой серией; это не
  маскируется редакцией состава.
- Production rollback после появления новых revision/run/result выполняется
  совместимым релизом без удаления append-only таблиц.
