# Приемка грантового управленческого отчета

Дата: 2026-07-26

Статус: контракт активного вертикального среза. До его завершения грантовый
контур в readiness matrix остается `Базово реализован`.

## 1. Цель

Руководитель должен получить проверяемый отчет `план -> распределение -> факт ->
остаток` по источнику финансирования и периоду. Администратор может читать отчет
и готовить исходные операционные данные, но не утверждает грантовые квоты,
распределения специалистам или выделения получателям.

## 2. Источники истины

## 3. Инвентаризация и gap analysis

| Область | Уже есть | Разрыв |
| --- | --- | --- |
| Источник | `FundingSource` для гранта, фонда, спонсора и других типов | Архивный источник нельзя выбрать в отчете |
| План услуги | `FundingServiceQuota.planned_sessions` и период | Ретроактивное редактирование не версионируется |
| Распределение | `FundingStaffAllocation`, быстрый вариант без квоты, периоды и ставка за занятие | Изменение и удаление стирают управленческую историю; нет фиксированной выплаты за проект |
| Получатель | `GrantRecipientAllocation` и счет в занятиях | Изменение количества не синхронизирует ledger; создание счета и выделения не объединено сервисной транзакцией |
| Факт услуги | Факт списанного занятия учитывает участника группы, специалиста и период назначения | Это текущий исправленный факт, а не зафиксированный снимок ранее сданного отчета |
| Баланс периода | Начальный остаток, движения и текущий баланс | Начальный и текущий остатки не вычисляются на границах периода; даты движений и занятий смешаны |
| Полномочия | Экран закрыт от специалиста | Все операторы могут менять квоты, что противоречит PRD |
| Выгрузка | CSV с балансами, квотами и получателями | Повторяет неоднозначные формулы экранного отчета |

## 4. Полномочия

| Действие | Администратор | Руководитель |
| --- | --- | --- |
| Читать отчет и CSV | Да | Да |
| Готовить расписание, списания и счета | Да | Да |
| Создать или изменить квоту услуги | Нет | Да |
| Распределить квоту специалисту | Нет | Да |
| Выделить грантовые занятия получателю | Нет | Да |
| Удалить плановую строку | Нет | Да |

Прямой HTTP-запрос администратора к управляющему действию получает `403`.
Интерфейс администратора не показывает команды, которых у него нет. Отдельный
workflow предложения квоты администратором не вводится в этом срезе: это
финансовое утверждение, для которого нужен собственный журнал решений.

## 5. Формулы отчета

Для каждой строки счета:

- `opening_balance` = `initial_amount` + все эффективные движения до начала
  периода;
- `inflows` = сумма положительных движений внутри периода;
- `outflows` = модуль суммы отрицательных движений внутри периода;
- `closing_balance` = `opening_balance + inflows - outflows`;
- `current_balance` = фактический ledger-остаток на момент построения и
  показывается только как справочная величина.

Итоги группируются по `BalanceAccount.unit`. Рубли и занятия никогда не
складываются в одно значение.

Эффективная дата движения:

- для списания занятия с сохраненным участником или занятием — дата оказания
  услуги из snapshot/занятия;
- для пополнения, перевода, конвертации и корректировки — дата создания
  проводки;
- возврат через correction отражается датой решения о возврате, исходное
  списание остается в периоде услуги.

План и факт:

- план по счету включает черновики, предложения, брони, согласованные,
  проведенные занятия и неявки; отмененные и исходные перенесенные слоты
  исключаются;
- общий факт квоты услуги — уникальные списанные занятия;
- факт специалиста — его назначения на списанные занятия;
- в групповом занятии каждый назначенный специалист получает один факт,
  общий факт услуги остается одним занятием;
- факт учитывается только внутри периода квоты/распределения;
- превышение факта над планом показывает отрицательный остаток и отдельный
  критический сигнал, а не маскируется нулем;
- выделение получателю считает только действующие списания выбранной услуги с
  его счета.

Отчет строится и для архивного источника и включает архивные счета, иначе
закрытый проект становится недоступен для проверки. Архивный источник
открывается только для чтения; перед изменением руководитель должен явно
восстановить его.

## 6. Границы текущего среза

В срез входят:

1. единые формулы баланса на начало и конец периода;
2. одинаковые формулы в HTML и CSV;
3. автоматическое построение `/grants/<source_id>/` за период источника или
   текущий календарный год;
4. разделение read и manage permissions;
5. focused service/view/role tests и browser smoke двух ролей.

Миграция БД не нужна. `operations/models.py` и migration chain не изменяются.

## 7. Отдельные опасные срезы

После приемки отчета отдельными контрактами проектируются:

1. append-only версии грантового плана и распределений с автором, основанием и
   решением руководителя;
2. безопасный сервис выделения получателю через ledger вместо изменения
   `initial_amount`;
3. фиксированная зарплата по гранту и контроль общего бюджета оплаты;
4. снимок закрытого/сданного донорского отчета и корректирующие версии;
5. ограничения пересекающихся периодов и PostgreSQL-сериализация параллельного
   распределения квоты.

Старые строки нельзя backfill-ить вымышленными авторами или датами решения.
Один DB owner проектирует и выполняет эти миграции после отдельного preflight.

## 8. Acceptance criteria

- исторический период показывает opening/closing, не сегодняшний остаток под
  видом остатка периода;
- итоги в рублях и занятиях показаны раздельно;
- поздняя обычная проводка не попадает в более ранний период;
- списание занятия относится к дате услуги;
- перевод и correction входят в поступления/расход периода по знаку;
- архивный источник открывается по прямому URL;
- руководитель выполняет полный CRUD существующих плановых сущностей;
- администратор читает тот же отчет и CSV, не видит управляющих команд и
  получает `403` по прямым управляющим URL;
- специалист получает `403`, а не доступ к данным;
- focused tests, Django check, Ruff и browser smoke проходят;
- после полного regression обновляется одна строка readiness matrix.

Дополнительные quality gates после независимого review:

- факт квоты требует одновременно решения `Списать` по выбранному источнику
  и существующей debit-проводки; расхождение показывается отдельным критическим
  сигналом;
- прямое распределение без `service_quota` не скрывается при наличии квоты
  той же услуги;
- ledger-балансы агрегируются на стороне БД, а число SQL-запросов не растет
  на каждый счет или `GrantRecipientAllocation`;
- скидки и сертификаты дедуплицируются в итогах по одному получателю;
- архивный источник остается read-only даже при невалидном периоде формы;
- CSV штатно экранирует `;`, кавычки и переводы строк и нейтрализует формулы,
  начинающиеся с `=`, `+`, `-` или `@`.
