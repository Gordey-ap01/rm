# Контракт среза: передача расчетного листа в выплату и фиксация выплаты

Дата: 2026-07-25

Статус: implemented

## Основание

`docs/01-prd.md`, разделы 2 и 4, и
`docs/51-payroll-director-approval-contract.md`: утверждение и выплата
расчетного листа входят в исключительные полномочия руководителя. В текущей
модели существуют статусы `sent` и `paid`, но отсутствуют доменные переходы,
реквизиты фактической выплаты и неизменяемый журнал этих действий.

Этот контракт следует ADR-004: финансовый процесс получает собственные
типизированные записи, а не общий workflow engine.

## Граница среза

Входит:

1. Только руководитель переводит утвержденный `PayrollSheet` в `sent`.
2. Только руководитель фиксирует один полный фактический платеж по листу и
   переводит его в `paid`.
3. Система одновременно и атомарно переводит все начисления строк листа в
   `paid`, сохраняет реквизиты выплаты и append-only журнал состояния.
4. Администратор видит состояние и реквизиты, но не видит и не может вызвать
   финансовые команды.
5. Экран листа показывает понятные следующие действия, историю и факт
   выплаты; мобильная ширина не меняет полномочия.

Не входит:

- частичная выплата, доплата, возврат, сторно и отмена после `approved`;
- банковская интеграция, выгрузка платежного поручения и отправка уведомления
  специалисту;
- создание `Payment`, `LedgerEntry` или `CenterExpense` при выплате зарплаты;
- расчёт налогов, удержаний и бухгалтерский учёт расходов центра;
- изменение уже утвержденных ставок, строк или суммы расчетного листа.

## Зафиксированное значение состояний

| Состояние | Значение | Кто выполняет | Разрешенный следующий переход |
| --- | --- | --- | --- |
| `draft` | Подготовленный, изменяемый лист начислений | администратор или руководитель | `approved` |
| `approved` | Руководитель проверил сумму и зафиксировал начисления | руководитель | `sent` |
| `sent` | Руководитель передал лист во внутренний контур фактической выплаты | руководитель | `paid` |
| `paid` | По листу зафиксирована одна полная фактическая выплата | руководитель | нет |
| `cancelled` | Исторический статус, вне данного среза | вне данного среза | нет |

`sent` в этом срезе означает внутреннее разрешение/передачу в выплату, а не
уведомление специалиста и не подтверждение банка. Такое разделение сохраняет
достоверность статуса до появления интеграции с банком или бухгалтерией.

## Полномочия

| Действие | Администратор | Руководитель | Проверка |
| --- | --- | --- | --- |
| Просмотр листа, строк и выплаты | да | да | existing admin access |
| Создание draft-листа | да | да | существующий контур табеля |
| Утверждение | нет | да | view и service |
| Передача в выплату (`sent`) | нет | да | view и service |
| Фиксация выплаты (`paid`) | нет | да | view и service |
| Изменение/удаление payout и журнала | нет | нет | неизменяемые записи, Django admin read-only |

Проверка в service является обязательной: скрытая кнопка не считается защитой.

## Модель данных

### `PayrollPayout`

Отдельная нормализованная сущность фактической зарплатной выплаты:

- `payroll_sheet`: `OneToOneField(PayrollSheet, on_delete=PROTECT)`;
- `amount`: `Decimal(12, 2)`, строго больше нуля и равна зафиксированной
  `PayrollSheet.total_amount` в transaction service;
- `method`: `bank_transfer`, `cash`, `other`;
- `paid_at`: дата фактической выплаты;
- `reference`: необязательный номер платежа/кассового документа;
- `note`: необязательное пояснение;
- `recorded_by`: обязательный `PROTECT` FK на руководителя;
- inherited `created_at`/`updated_at`.

`Payment` намеренно не переиспользуется: его предметная область — пополнение
счёта получателя и последующая ledger-проводка, а не расход центра на оплату
труда. `PayrollPayout` также не является `CenterExpense`: у последней другой
контрагент и отдельный процесс распределения источников. Связь с учетом
расходов будет отдельным контрактом, когда будут определены правила
бухгалтерского отражения без двойного учета.

### `PayrollSheetLifecycleEvent`

Типизированная append-only история финансовых переходов:

- `payroll_sheet`: `ForeignKey(PayrollSheet, on_delete=PROTECT)`;
- `event_type`: `sent` или `paid`;
- `status_from` и `status_to`;
- `actor`: обязательный `PROTECT` FK;
- `actor_role_snapshot`: единственное допустимое значение `director`;
- `note`: обязательное осмысленное основание для `sent`, необязательное для
  `paid` (реквизиты находятся в `PayrollPayout`);
- `occurred_at`: server-side time;
- inherited timestamps.

Одна выплата возможна только однажды за счет `OneToOneField`. Повторная
команда не создает ни второй payout, ни второй журнал: service заново читает
и блокирует лист, видит неразрешенное состояние и возвращает ошибку.

### Ограничения и индексы

- DB `CHECK`: сумма payout положительна.
- DB `CHECK`: у event допустимы только `approved -> sent` и `sent -> paid`;
  снимок роли равен `director`.
- `PayrollPayout`: индекс `paid_at` для отчета руководителя; one-to-one уже
  создает уникальный индекс листа.
- `PayrollSheetLifecycleEvent`: индексы
  `(payroll_sheet, -occurred_at)` и `(event_type, -occurred_at)`.
- Все денежные поля — `Decimal`, без float.

## Транзакции и конкурентность

`send_payroll_sheet` и `record_payroll_payout` выполняются в
`transaction.atomic()` в следующем порядке блокировок:

1. `PayrollSheet`;
2. его `PayrollSheetLine` по PK;
3. соответствующие `PayrollAccrual` по PK;
4. payout, если он уже существует.

Переход в `sent` разрешен только из `approved`, при сохранении утвержденного
состояния всех accruals. Переход в `paid` разрешен только из `sent`, создает
payout, меняет статус листа и всех его accruals в одной транзакции и затем
добавляет event. Сумма берется из заблокированных строк и должна совпасть с
итогом листа и переданной суммой; клиент не может подменить итог.

## Миграция и существующие данные

Миграция только добавляет две новые таблицы и не меняет старые строки:

- существующие `draft` и `approved` листы продолжают обычный путь;
- данные для исторических `paid` листов не выдумываются и не backfill-ятся;
- новый audit появляется с первой новой передачей в выплату.

До появления первой выплаты миграция технически обратима. После появления
финансовых записей откат в production запрещен: исправление делается только
новой forward-миграцией, чтобы не уничтожить историю выплаты.

## UI и аудит

- У руководителя на `approved` есть команда «Передать в выплату» с обязательным
  основанием; на `sent` — форма «Зафиксировать выплату» с датой, способом,
  суммой, номером документа и комментарием.
- У администратора вместо команд виден текущий этап и история, без POST
  возможности.
- В `paid` показываются дата, способ, сумма, номер документа и кто зафиксировал.
- Новые модели добавляются в auditlog и в Django admin только для чтения:
  запрещены add/change/delete.

## Проверки приемки

1. Руководитель может перевести корректный `approved` лист в `sent`; создается
   ровно один event.
2. Не-руководитель получает `403` в view и `PermissionDenied` в service для
   обоих переходов.
3. Выплата допускается только после `sent`, только один раз и только на полную
   сумму листа.
4. После выплаты лист и все его accruals имеют `paid`, payout и event либо
   существуют вместе, либо не существуют вовсе при ошибке.
5. Конкурентные запросы на выплату не приводят к двойной выплате — проверка
   запускается на PostgreSQL.
6. Администратор не видит финансовые кнопки; проверка desktop и mobile в
   настоящем браузере не показывает горизонтальную прокрутку или console error.
7. Старые payroll-тесты, проверки миграций, `django check` и полный тестовый
   набор проходят на SQLite и PostgreSQL.

## Открытое расширение

Когда появится подтвержденный процесс бухгалтерии, следующий контракт может
добавить внешний платежный документ, частичные платежи и корректировочные
операции. Он не меняет смысл уже сохраненного `PayrollPayout`; новые операции
будут ссылаться на него, а не редактировать факт выплаты.
