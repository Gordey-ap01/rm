Дата: 2026-06-24

Статус: рабочий план после старта реализации. Владелец БД уже внес первые миграции новой модели занятия, начислений и грантовых квот.

Базовый контракт доменной модели: `docs/07-updated-domain-model-after-interview.md`.

Актуализация 2026-06-29: этапы новой модели занятий, представителей, кабинетов,
грантовых квот, payroll, preview-импорта и основные UX-срезы уже частично
реализованы; свежий источник статуса - `docs/current-state.md`. Этот документ
остается контрактом безопасного распараллеливания: один владелец БД/миграций,
раздельные write-scope для coding-агентов и read-only аудиторы только без правки
файлов. Read-only reviewer можно подключать параллельно для проверки текущего
diff, если он не меняет код, не трогает `operations/models.py` и не создает
миграции.

Актуализация 2026-07-01/2026-07-02: Stage 5 UX/UI табличная стабилизация закрыта на уровне
финального аудита `data-label`. Первый persisted-срез переноса расписания по
`docs/09-cascade-reschedule-domain-slice.md` реализован: модели плана и шагов,
миграция `0018`, сервис генерации/валидации/применения одного шага и минимальный
UI. Согласования по валидному шагу плана также реализованы через
`AppointmentConfirmation.reschedule_step` и миграцию `0019`; одиночный шаг с
`requires_room_override=True` теперь применяется только через явное разрешение
администратора и сохраняет `AppointmentRoomOverride`; реестр `/reschedule-plans/`
получил read-only периодные метрики руководителя. Следующие шаги этой зоны
по-прежнему требуют одного владельца БД/миграций: автоматическое применение после
подтверждений, длинные цепочки и новые правила массовых переносов нельзя отдавать
нескольким агентам одновременно, если они затрагивают `operations/models.py`,
миграции или сервис переноса.

## Можно ли уже приступать

Да, можно приступать, но не всем агентам сразу к коду. Сначала нужно выполнить один контролируемый вертикальный срез по новой модели занятия. Он меняет БД, расписание, финансы и UI, поэтому у него должен быть один владелец миграций.

Параллельная работа безопасна только там, где агенты не меняют одни и те же файлы и не создают конкурирующие миграции.

## Главные правила координации

1. Один владелец БД и миграций.
2. Только владелец БД меняет:
   - `operations/models.py`
   - `operations/migrations/*`
   - PostgreSQL constraints
   - backfill-миграции
3. Остальные агенты не меняют модели и миграции без письменного контракта от владельца БД.
4. Каждый вертикальный срез должен включать:
   - модель/миграцию, если нужна;
   - доменный сервис или валидацию;
   - UI;
   - тесты;
   - проверку существующих сценариев.
5. Нельзя записывать Excel-импорт в БД до стабилизации новой модели представителей и групповых занятий. Безопасный preview-импорт без записи уже допустим.
6. Нельзя удалять старые поля `Appointment.child`, `Appointment.staff_member`, `Appointment.billing_account` до полного backfill и переключения отчетов.
7. Нельзя делать большую перепись UI на React до доказанной необходимости.

## Последовательность работ

### Этап 0. Подготовка контракта

Статус: выполнено частично.

Уже есть:

- `docs/07-updated-domain-model-after-interview.md`
- этот документ

Осталось перед кодом:

- назначить агента A владельцем миграций;
- решить, работаем на одной ветке или на отдельных ветках;
- убедиться, что локально проходят текущие тесты до изменений.

Acceptance criteria:

- есть один владелец `operations/models.py`;
- все агенты знают запрет на миграции;
- текущий baseline тестов зафиксирован.

### Этап 1. БД: новая модель занятия и представителей

Владелец: агент A.

Состав:

- добавить `RecipientRepresentative`;
- добавить `AppointmentParticipant`;
- добавить `AppointmentStaffAssignment`;
- добавить `AppointmentRoomOverride`;
- добавить новые поля `Room`;
- добавить backfill из старой модели;
- временно сохранить старые поля `Appointment.child`, `Appointment.staff_member`, `Appointment.billing_account`.

Acceptance criteria:

- существующие занятия после миграции имеют одного участника и одного специалиста;
- существующие представители перенесены в `RecipientRepresentative`;
- миграция не удаляет данные;
- старые экраны не падают;
- тесты покрывают backfill.

### Этап 2. Доменная проверка расписания

Владелец: агент A.

Состав:

- переписать проверку конфликтов получателя через `AppointmentParticipant`;
- переписать проверку конфликтов специалиста через `AppointmentStaffAssignment`;
- заменить кабинетный constraint на сервисную проверку вместимости;
- убрать или заменить PostgreSQL constraint `no_room_overlap_active_appointments`;
- добавить транзакционную проверку кабинетных лимитов.

Acceptance criteria:

- индивидуальное занятие блокирует специалиста на время занятия;
- один получатель не может быть в двух активных занятиях одновременно;
- большой зал с лимитом 2 специалистов допускает двух специалистов одновременно;
- кабинет с лимитом 1 получатель предупреждает при попытке добавить второго;
- override кабинета сохраняет причину и автора.

### Этап 3. Минимальный UI групповых занятий

Владелец: агент B.

Начинается после стабильного контракта от агента A.

Состав:

- переключатель индивидуальное/групповое;
- выбор нескольких получателей;
- выбор одного или нескольких специалистов;
- показ лимитов кабинета;
- предупреждение по конфликтам;
- hold-to-override;
- детальная карточка группового занятия.

Acceptance criteria:

- индивидуальное занятие создается не сложнее, чем сейчас;
- групповое занятие создается с несколькими детьми;
- несколько специалистов отображаются в карточке;
- предупреждения не требуют чтения технических ошибок;
- после ошибки форма сохраняет введенные значения.

### Этап 4. Представители и рассылки

Владелец: агент C.

Может начаться после миграции `RecipientRepresentative`, параллельно с UI расписания.

Состав:

- форма получателя с вложенным добавлением представителя;
- несколько представителей в карточке получателя;
- основной представитель;
- подписант договора;
- флажок получения расписания;
- отправка подтверждений всем выбранным адресатам.

Статус на текущей ветке: карточка получателя, добавление/редактирование связи представителя и рассылка по `receives_schedule` реализованы. Вложенное создание нового представителя прямо внутри формы получателя еще не сделано.

Acceptance criteria:

- можно создать получателя без представителя;
- можно создать получателя и представителя в одной форме — не выполнено;
- можно добавить маму и бабушку одному ребенку — выполнено через карточку получателя;
- расписание уходит только тем, у кого включен флажок — выполнено;
- основной представитель виден в карточке — выполнено.

### Этап 5. Списания в группах

Владелец: агент A, UI может подключить агент B.

Состав:

- `LedgerEntry` связывается с `AppointmentParticipant`;
- списание отдельно по каждому получателю;
- старые списания остаются читаемыми;
- отмена списания создает корректировку или отвязку по согласованному правилу.

Acceptance criteria:

- в группе можно списать одного ребенка и не списать другого;
- остатки по каждому счету корректны;
- низкие остатки считаются по новой модели;
- отчеты не теряют старые ledger-записи.

### Этап 6. Зарплаты и гранты

Владелец моделей: агент A.

Отчеты и UI: агент D после добавления моделей.

Состав:

- `StaffCompensationRule` — реализовано;
- начисления в табеле специалиста только после решения `списать` — реализовано;
- `FundingServiceQuota` — реализовано;
- `FundingStaffAllocation` — реализовано;
- квоты в grant report — реализовано;
- `PayrollAccrual` — реализовано;
- `PayrollSheet` — реализовано;
- `PayrollSheetLine` — реализовано;
- `GrantRecipientAllocation` — реализовано;
- мастер быстрого сценария `специалист + количество занятий` — реализовано.

Acceptance criteria:

- руководитель задает ставку по услуге и длительности — частично выполнено;
- руководитель задает отдельные грантовые ставки — выполнено через `funding_source` и `FundingStaffAllocation.session_pay_amount`;
- для группы можно выбрать принцип начисления — выполнено через `StaffCompensationRule.session_scope`, `StaffCompensationRule.group_pay_policy`, `StaffCompensationRule.group_fixed_amount` и snapshot-поля `PayrollAccrual`;
- расчетный лист формируется за произвольный период — выполнено;
- грантовая квота распределяется по специалистам — выполнено в модели, отчете и UI.

### Этап 7. Расходы, оборудование, договоры

Владелец: отдельный агент после стабилизации этапов 1-6.

Состав:

- хозяйственные расходы;
- коммунальные платежи;
- оборудование;
- доноры/контрагенты;
- договоры пожертвования;
- договоры с получателями услуг.

Acceptance criteria:

- руководитель видит расходы по категориям и источникам;
- расход может быть оплачен несколькими источниками;
- можно сформировать договор пожертвования из шаблона;
- отчет для спонсора строится без лишних персональных данных.

## Что можно делать параллельно уже сейчас

- Read-only реестр `/reschedule-plans/` уже добавлен без новых миграций.
- `staff_absence` persisted-план из экрана массового переноса уже добавлен без новых миграций; он создает pending `review_conflict` шаги и не отменяет занятия.
- UI ручного разбора `review_conflict` уже добавлен без новых миграций; закрытие шага возможно только после фактического переноса или отмены исходного занятия.
- Read-only реестр уже усилен управленческим фильтром `focus` и маркерами ручного разбора, устаревших шагов, ошибок, ожидания ответов, отказов и готовых к применению шагов.
- Реестр уже показывает read-only периодные метрики, а `apply_step()` закрывает альтернативные шаги того же исходного занятия после применения одного варианта. Текущие `move` шаги для одного `source_appointment` нельзя отдавать разным агентам как независимую цепочку.
- Для следующего этапа создан `docs/10-reschedule-chain-dependencies-contract.md`: схема `AppointmentRescheduleChain`/`AppointmentRescheduleStepDependency` и nullable chain-поля на step. Первый миграционный срез выполнен в `operations.0021_reschedule_chains`.
- Следующий срез - сервис построения цепочки без применения. Его может делать один владелец `operations/services/rescheduling_plans.py`; UI-агент может подключаться только после фиксации сервисного контракта и без правки моделей/миграций.
- До следующего согласованного контракта нескольким агентам нельзя параллельно менять `operations/models.py`, `operations/migrations/*`, `operations/services/rescheduling_plans.py` и `operations/views/rescheduling_plans.py`.
- Безопасные параллельные задачи сейчас: read-only code review, UX-черновик dashboard руководителя по планам переноса, документация production/backup/SMTP, но без правки моделей, миграций и сервисов переноса.
