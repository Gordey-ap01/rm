# **Архитектурный план и проектирование базы данных для автономной системы управления реабилитационным центром**

## **1\. Введение: Операционный контекст и стратегические императивы**

Проектирование информационной системы для реабилитационного центра с пропускной способностью около 100 пациентов в день представляет собой задачу, выходящую за рамки стандартных решений класса EHR (Electronic Health Record). В отличие от поликлиник с эпизодическими визитами или стационаров с койко-днями, реабилитация характеризуется высокой интенсивностью и цикличностью процессов. При среднем показателе 4-5 процедур на пациента в день система должна безотказно обрабатывать и синхронизировать 400-500 событий ежедневно, что составляет порядка 10 000–12 000 уникальных записей в месяц, не считая финансовых транзакций и складских операций.

Специфика задачи, поставленной в запросе, диктует необходимость гибридного подхода. С одной стороны, требование локального развертывания (Local-First) на Windows через Docker указывает на приоритет суверенитета данных, независимости от облачных провайдеров и устойчивости к сбоям интернет-соединения. Это особенно актуально в условиях регуляторных требований РФ (152-ФЗ), подразумевающих строгий контроль над местонахождением серверов с персональными данными.1 С другой стороны, функциональные требования — автоматическое расписание, учет смешанных платежей (гранты/личные средства) и логистика «форс-мажоров» — требуют вычислительной мощности и гибкости, недоступных в коробочных no-code решениях.

В данном отчете представлено глубокое исследование и проектирование «Идеальной Системы» (Ideal System Architecture), основанной на концепции **«Low-Code Core, High-Code Edge»**. Мы используем NocoDB как визуальный интерфейс и слой управления данными, PostgreSQL как надежное хранилище, и микросервис на Python как «интеллектуального агента» для решения алгоритмических задач.

### **1.1. Анализ критических ограничений и требований**

Анализ предоставленных материалов 1 и лучших практик 2 позволяет выделить ключевые векторы проектирования:

1. **Детерминированность данных:** В медицине недопустима приблизительность. Если процедура «Бобат-терапия» требует 45 минут и наличия специалиста категории А, система не должна позволять записать на нее стажера или выделить 30 минут. Это требует реализации жестких ограничений (Constraints) на уровне схемы БД.  
2. **Финансовая слоистость:** Оплата одного курса лечения может поступать из трех источников: 30% — государственный грант, 50% — благотворительный фонд, 20% — доплата пациента. Система должна поддерживать «каскадное списание» (Waterfall Billing), автоматически переключаясь между кошельками пациента при исчерпании лимитов.  
3. **Логистика «Форс-мажора»:** В отличие от отмены встречи в календаре, отмена сеанса реабилитации требует сдвига всей последующей цепочки занятий (session shifting), чтобы сохранить терапевтический интервал и последовательность курса.  
4. **Автономность:** Использование Docker Compose позволяет инкапсулировать всю среду. Это исключает проблему «it works on my machine», критичную для локальных инсталляций на Windows, где системные библиотеки могут конфликтовать.

**2\. Архитектура системы и технологический стек**

Для реализации поставленных задач предлагается архитектура, состоящая из трех изолированных, но тесно интегрированных контейнеров. Данная топология обеспечивает баланс между простотой администрирования и мощностью функционала.

### **2.1. Компонентная база (The Triad)**

| Компонент | Технология | Обоснование выбора |
| :---- | :---- | :---- |
| **База Данных (Storage)** | **PostgreSQL 16** | Для нагрузки в 100 пациентов/день SQLite (стандартный для NocoDB) становится узким местом из\-за блокировок при записи (write-locking). PostgreSQL обеспечивает MVCC (многоверсионность), поддержку JSONB для гибких медицинских анкет и строгую ссылочную целостность, необходимую для медицинских данных.4 |
| **Интерфейс (UI/Admin)** | **NocoDB** | Выполняет роль «Headless CMS» для базы данных. Превращает PostgreSQL в умные таблицы, генерирует REST/GraphQL API и предоставляет готовый интерфейс для врачей и администраторов. Это экономит сотни часов разработки фронтенда.2 |
| **Логика (Compute)** | **Python (FastAPI)** | NocoDB не умеет решать задачи комбинаторной оптимизации (составление расписания). Для этого используется отдельный контейнер с Python, который слушает вебхуки от NocoDB, выполняет тяжелые вычисления (используя библиотеки типа Google OR-Tools или Pandas) и пишет результат обратно через API.6 |

### **2.2. Топология развертывания Docker Compose на Windows**

Развертывание на Windows требует особого внимания к файловой системе (WSL2 vs Hyper-V). Рекомендуемая конфигурация docker-compose.yml должна включать:

* **Volume Mapping (Персистентность):**  
  * Данные PostgreSQL монтируются в локальную папку хоста (например, ./data/postgres). Это позволяет администратору делать «холодные» бэкапы простым копированием папки при остановленном контейнере, что критично для не-IT персонала.  
  * Файловое хранилище NocoDB (сканы МРТ, договоры) монтируется в ./data/uploads. Это обеспечивает прямой доступ к файлам без необходимости «вытаскивать» их из контейнера.5  
* **Networking:**  
  * Создается внутренняя сеть rehab\_net. Контейнер Python (worker) не выставляет порты наружу (expose), общаясь только внутри сети с NocoDB и PostgreSQL, что повышает безопасность.  
* **Restart Policy:** unless-stopped гарантирует, что система автоматически поднимется после перезагрузки сервера (например, после обновления Windows).

### **2.3. Интеграция Python-воркера**

Ключевой элемент «умной» системы — связь между NocoDB и Python.

1. **Триггер:** В интерфейсе NocoDB создается поле типа «Button» (Кнопка) с названием «Сформировать расписание».  
2. **Действие:** Нажатие кнопки отправляет POST-запрос на http://python-worker:8000/api/schedule/generate с передачей ID пациента.  
3. **Обратная связь:** Поскольку вебхук асинхронен, Python-скрипт первым делом обновляет статус пациента в таблице на «Вычисляется...», а по завершении — на «Готово». Администратор видит изменение статуса в реальном времени благодаря вебсокетам NocoDB.7

**3\. Проектирование схемы базы данных (Database Schema)**

Проектирование схемы — это фундамент. Ошибки на этом этапе (например, отсутствие нормализации или неправильные типы данных) приведут к хаосу при масштабировании. Ниже приведена детальная структура таблиц, учитывающая все требования, включая «кадры», «склад» и «финансы».

### **3.1. Блок «Субъекты» (Registries)**

#### **3.1.1. Таблица patients (Пациенты)**

Центральная сущность.

* id (UUID, PK): Использование UUID обязательно для предотвращения конфликтов при возможном слиянии баз данных в будущем.  
* full\_name (Text): Хранение ФИО одной строкой или тремя полями (last, first, middle) для корректной сортировки по-русски.  
* dob (Date): Дата рождения. Критически важна, так как длительность процедур для детей и взрослых различается.  
* status (Enum): Active, Discharged, Waitlist, OnHold.  
* mobility\_aid (Enum): None, Wheelchair, Stretcher. *Инсайт:* Это поле используется алгоритмом расписания для фильтрации кабинетов (например, нельзя назначить колясочника на 2-й этаж без лифта).  
* primary\_diagnosis\_icd (Text): Код МКБ-10.

#### **3.1.2. Таблица guardians (Представители/Опекуны)**

Учитывая специфику (дети-инвалиды, пожилые люди), отношение «Один-ко-Многим» недостаточно. Нужна связь «Многие-ко-Многим».

* **Таблица guardians:** id, fio, phone, email.  
* **Таблица-связка patient\_guardians:**  
  * patient\_id (FK)  
  * guardian\_id (FK)  
  * relationship\_type (Enum): Mother, Father, Caseworker (для детдомовских детей).  
  * is\_primary\_payer (Boolean): Кто подписывает акты выполненных работ.

#### **3.1.3. Таблица staff (Кадры)**

Система должна поддерживать как штатных сотрудников, так и внешних консультантов.

* id (UUID, PK)  
* fio (Text)  
* role (Enum): Physician, Therapist, Admin, Nurse.  
* **employment\_type (Enum):** Salaried (Оклад), Contractor (Сдельная). *Инсайт:* Это поле определяет логику расчета зарплаты в конце месяца.  
* color\_code (Hex): Для визуализации в календаре.  
* max\_daily\_hours (Int): Ограничение для алгоритма расписания (например, не более 6 часов контактной работы).

### **3.2. Блок «Клиническая деятельность и Логистика»**

#### **3.2.1. Таблица services (Каталог услуг)**

Здесь определяется бизнес-логика процедур.

* id (PK)  
* name (Text): "ЛФК Групповая", "Массаж шейно-воротниковой зоны".  
* duration\_min (Int): Стандартная длительность (30, 45, 60 мин).  
* **is\_group (Boolean):** Флаг группового занятия.  
* **min\_participants / max\_participants (Int):** Ограничения для авто-расписания. Группу из 1 человека создавать нерентабельно, больше 6 — опасно.  
* required\_resource\_type (Enum): Gym, Pool, MassageTable, ConsultationRoom. Связывает услугу с типом помещения.

#### **3.2.2. Таблица resources (Помещения и Оборудование)**

* id (PK)  
* name (Text): "Кабинет 101", "Бассейн малый".  
* type (Enum): Совпадает со справочником в services.  
* is\_accessible (Boolean): Доступность для колясочников.  
* maintenance\_status (Enum): Active, Repair, Cleaning.

#### **3.2.3. Таблица schedule\_slots (Слоты расписания)**

Самая нагруженная таблица ("Сердце" системы).

* id (UUID, PK)  
* start\_time (Timestamp with TZ)  
* end\_time (Timestamp with TZ)  
* staff\_id (FK)  
* resource\_id (FK)  
* service\_id (FK)  
* **status (Enum):** Scheduled, Completed, Cancelled\_Patient, Cancelled\_Facility (Форс-мажор), No\_Show.  
* **group\_id (UUID, Nullable):** Если занятие групповое, здесь хранится ID группы, связывающий несколько записей пациентов.

#### **3.2.4. Таблица session\_participants (Участники сеансов)**

Разделение слота и участника необходимо для групповых занятий.

* slot\_id (FK)  
* patient\_id (FK)  
* treatment\_plan\_id (FK): Ссылка на назначение.  
* **sequence\_number (Int):** Номер сеанса в курсе (например, 5 из 10). *Инсайт:* Это критически важно для алгоритма сдвига расписания. При отмене сеанса №5, система должна найти следующий доступный слот и назначить его именно как №5, сдвинув старый №6 на позицию №7.10

### **3.3. Блок «Финансы и Смешанная оплата»**

Реабилитационные центры часто работают по схеме «Квота \+ Доплата». Стандартная модель "один счет — одна оплата" здесь не работает. Предлагается модель **«Кошельков» (Wallets)**.

#### **3.3.1. Таблица funding\_sources (Источники финансирования)**

* id (PK)  
* name (Text): "ОМС", "Фонд 'Подари Жизнь'", "Личные средства".  
* type (Enum): Grant, Insurance, Private.

#### **3.3.2. Таблица patient\_wallets (Балансы пациентов)**

* id (PK)  
* patient\_id (FK)  
* funding\_source\_id (FK)  
* **balance\_sessions (Int):** Количество оплаченных сеансов (например, Фонд оплатил 20 занятий ЛФК).  
* **balance\_money (Decimal):** Депозит в валюте.  
* expiry\_date (Date): Срок действия гранта.

#### **3.3.3. Таблица billing\_transactions (Транзакции)**

Связывает факт оказания услуги (schedule\_slots) с списанием средств.

* id (PK)  
* slot\_id (FK)  
* wallet\_id (FK)  
* amount (Decimal)  
* timestamp (DateTime)

**Логика работы:** При завершении сеанса (status \-\> Completed) триггер БД или Python-скрипт проверяет кошельки пациента. Приоритет списания настраивается (сначала Грант, потом Личные). Если грант покрывает 100%, списывается 1 session\_unit. Если смешанная (50/50), создаются две транзакции к разным кошелькам.

### **3.4. Блок «Склад и Учет материалов» (Inventory)**

Медицинские расходники (тейпы, гели, одноразовые простыни) должны списываться автоматически.

#### **3.4.1. Таблица inventory\_items**

* id (PK)  
* name (Text)  
* sku (Text)  
* current\_stock (Decimal): Текущий остаток.  
* unit (Enum): pcs, ml, meters.

#### **3.4.2. Таблица service\_bom (Bill of Materials)**

Связывает услугу с расходом.

* service\_id (FK)  
* item\_id (FK)  
* quantity (Decimal): Сколько списывать за 1 сеанс.

**Логика:** При статусе Completed система смотрит BOM услуги и создает запись в таблице движения товаров (inventory\_log), уменьшая остаток.

**4\. Алгоритмы автоматизации и «Кнопка Авто-Расписания»**

Запрос на «авто-расписание» — самый технически сложный элемент. Это задача удовлетворения ограничений (Constraint Satisfaction Problem \- CSP).

### **4.1. Формализация задачи для Python**

Скрипт на Python (используя библиотеку ortools или pandas для простой эвристики) должен решить следующую задачу:

**Дано:**

1. Пациент P с назначением: "ЛФК, 10 сеансов, 3 раза в неделю, предпочтительно утро".  
2. Доступность врачей (Staff Availability).  
3. Доступность залов (Resource Availability).

**Ограничения (Hard Constraints):**

* Врач и Зал должны быть свободны одновременно в интервале \`\`.  
* Интервал между сеансами \>= 1 день (для восстановления).  
* Врач должен иметь соответствующую специализацию.

**Алгоритм «Поиск и Бронирование»:**

1. Python получает запрос через API.  
2. Выгружает из БД «сетку занятости» (матрицу времени) для нужных ресурсов.  
3. Ищет свободные «окна», соответствующие длительности услуги.  
4. Фильтрует окна по предпочтениям пациента (Soft Constraints).  
5. Бронирует слоты в транзакции, присваивая им sequence\_number (1, 2, 3...).

### **4.2. Обработка Форс-мажоров (Rescheduling Logic)**

Когда врач заболевает, администратор помечает его как Unavailable на конкретный день.

**Алгоритм «Волна» (Ripple Effect):**

1. Найти все слоты этого врача в диапазоне дат.  
2. Изменить статус на Cancelled\_Facility.  
3. Для каждого затронутого пациента:  
   * Взять номер отмененного сеанса (например, №4).  
   * Найти *следующий* запланированный сеанс (№5) и переназначить его как №4 (сдвиг по смыслу, но не по времени).  
   * Добавить новый сеанс в конец курса, чтобы общее количество (10) сохранилось.  
   * Если свободных слотов нет, поместить пациента в Priority Waitlist.

Этот механизм гарантирует, что пациент получит полный курс лечения, даже если сроки сдвинутся.12

**6\. Финансовая и Кадровая подсистема (HR & Finance)**

### **6.1. Кадровый учет и Табелирование**

Система должна автоматически генерировать табель рабочего времени (Timesheet).

* **Штатные сотрудники:** Python-скрипт суммирует часы из расписания (фактически отработанное время) и сравнивает с плановым графиком.  
* **Внешние врачи (Сдельная оплата):** В конце месяца запускается скрипт calculate\_contractor\_payouts.  
  * Логика: SELECT SUM(service\_cost \* doctor\_share\_percentage) FROM schedule\_slots WHERE status='Completed' AND staff\_id=X.  
  * Результат записывается в таблицу payouts, которую бухгалтер может экспортировать в Excel/1C.14

### **6.2. Учет Хозяйственной Деятельности (Facility Management)**

Для реабилитационного центра критически важно состояние помещений (доступность, чистота).

* **Таблица housekeeping\_logs:** Связана с resources. Хранит график уборок (важно для бассейнов и стерильных зон).  
* **Статусы блокировки:** Если в таблице resources статус меняется на Maintenance (например, "Сломан подъемник"), триггер БД должен блокировать создание новых слотов в этом помещении и уведомлять администратора о необходимости переноса существующих записей.16

**7\. Исследование рынка и обоснование выбора (Research Insights)**

### **7.1. Почему не готовые МИС (Медицинские Информационные Системы)?**

Большинство российских МИС (Medesk, Renovation) — это облачные SaaS-решения.18 Они отличны для клиник, но:

1. **Стоимость:** Тарификация часто идет за "рабочее место". Для центра с большим штатом это дорого.  
2. **Жесткость:** Они плохо поддерживают специфику реабилитации (курсовое лечение, сложная логика списания грантов).  
3. **Локальность:** Они требуют интернета. Локальное развертывание (как требуется в запросе) у вендоров стоит миллионы рублей или невозможно.

### **7.2. Почему не Excel?**

При 100 пациентах в день Excel "умирает" на конкурентном доступе. Если два администратора одновременно попытаются записать пациента на 10:00 к одному врачу, Excel создаст коллизию. PostgreSQL с блокировками транзакций гарантирует, что запишется только один.

### **7.3. Масштабируемость**

Предложенная архитектура на Docker \+ Postgres легко масштабируется. Если центр вырастет до 500 пациентов, достаточно перенести контейнеры на более мощный сервер, не меняя код. Данные отделены от логики, а интерфейс (NocoDB) виртуализирован.

# **Глубокое исследование: Идеальная архитектура и БД для реабилитационного центра**

## **1\. Концептуальная модель системы**

### **1.1. Специфика реабилитации как бизнес-процесса**

Реабилитационный центр (РЦ) фундаментально отличается от классической клиники. В то время как клиника работает с дискретными событиями (визит к врачу \-\> диагноз \-\> рецепт), РЦ работает с **потоками (flows)** и **циклами**.

* **Цикличность:** Пациент назначается не на один прием, а на курс (10-20 сеансов). Это создает колоссальную нагрузку на календарь. Ручное планирование 100 пациентов \* 10 сеансов \= 1000 слотов — это источник ошибок.  
* **Мультидисциплинарность:** С одним пациентом работает команда (невролог, логопед, инструктор ЛФК). Данные должны быть доступны всем участникам процесса одновременно.  
* **Социальная составляющая:** Многие пациенты (особенно дети с ДЦП или пожилые после инсульта) зависят от опекунов. Система должна учитывать логистику сопровождающих.

### **1.2. Обоснование выбора стека "Local-First"**

Выбор локального запуска (On-Premise) на Windows через Docker является стратегически верным для РЦ по трем причинам:

1. **Безопасность данных (Data Sovereignty):** Медицинские данные (PHI/ПДн) остаются внутри периметра организации. Это снимает риски утечек через облачных провайдеров и упрощает аттестацию по требованиям регуляторов (ФСТЭК/Роскомнадзор для РФ).  
2. **Отказоустойчивость (Offline-First):** РЦ часто находятся за городом или в старых зданиях с нестабильным интернетом. Остановка работы регистратуры из\-за обрыва связи недопустима. Локальный Docker-контейнер продолжает работать даже без сети.  
3. **Экономическая эффективность:** Отсутствие ежемесячных платежей за SaaS (Software as a Service) за каждое рабочее место. Затраты идут только на "железо".

## ---

**2\. Техническая архитектура (Deep Dive)**

Мы строим систему по принципу **Микросервисы на Монолите**. Все сервисы живут на одном физическом сервере, но изолированы логически.

### **2.1. Стек технологий**

* **Хост:** Windows 10/11 Pro (с поддержкой WSL2) или Windows Server.  
* **Оркестратор:** Docker Compose.  
* **СУБД:** PostgreSQL 16\. (Почему не MySQL? Postgres лучше работает со сложными запросами и JSON-структурами, которые нужны для хранения параметров медицинских карт).  
* **Frontend/Backend:** NocoDB. Это "Low-Code" платформа, которая автоматически создает интерфейс и API поверх базы данных.  
* **Automation Worker:** Python 3.11 \+ FastAPI. Это "мозг" системы для сложных расчетов.  
* **Reverse Proxy:** Caddy или Nginx (опционально, для SSL внутри локальной сети).

### **2.2. Схема взаимодействия компонентов**

1. Пользователь (Администратор) открывает браузер \-\> localhost:8080 (NocoDB).  
2. NocoDB читает/пишет данные в контейнер db (PostgreSQL).  
3. При нажатии кнопки "Авто-расписание", NocoDB делает HTTP-запрос (Webhook) в контейнер worker (Python).  
4. worker подключается к db, считывает ограничения, генерирует слоты и пишет их обратно в db.  
5. NocoDB через вебсокеты обновляет интерфейс пользователя, показывая новые записи.

### **2.3. Хранение файлов (File Storage Strategy)**

Для хранения файлов (договоры, сканы, DICOM-снимки) в Docker на Windows критично правильно настроить тома (Volumes).

* **Ошибка новичка:** Хранить файлы внутри контейнера. При обновлении контейнера файлы пропадут.  
* **Решение:** Bind Mounts. В docker-compose.yml мы прописываем:  
  YAML  
  volumes:  
    \- C:\\RehabCenter\\Data\\Uploads:/usr/app/data/nc/uploads

  Это делает файлы доступными прямо в папке Windows, что позволяет легко делать резервные копии простым копированием папки на внешний диск.

## ---

**3\. Проектирование базы данных: Схема и Сущности**

База данных должна быть нормализована (3NF), чтобы избежать дублирования и аномалий данных.

### **3.1. Пациенты и Окружение**

* **patients**: Основная таблица.  
  * id (UUID)  
  * full\_name (Text)  
  * birth\_date (Date)  
  * passport\_data (JSONB) \- для гибкости.  
  * contraindications (Text) \- противопоказания (например, "эпилепсия" \-\> запрет на мигающий свет).  
* **guardians**: Опекуны.  
  * id, full\_name, contact\_info.  
* **rel\_patients\_guardians**: Таблица связей (Many-to-Many). Один опекун может водить двух детей, у одного ребенка может быть мама и папа.

### **3.2. Кадры и Ресурсы (HR & Facilities)**

* **staff**:  
  * id  
  * specialty (Enum: Physio, Speech, Neuro, Admin)  
  * **employment\_model** (Enum: Staff, External). Это поле определяет, платим ли мы оклад или % от процедуры.  
  * color (для календаря).  
* **rooms**:  
  * id, name, capacity (вместимость).  
  * resources (Array): \`\`.  
* **equipment**: Учет дорогостоящего оборудования (Локомат, БОС).  
  * id, name, serial\_number, next\_service\_date.

### **3.3. Услуги и Склад (Services & Inventory)**

* **services**:  
  * id, name, price\_base.  
  * duration\_minutes.  
  * is\_group (Boolean).  
* **inventory\_items**:  
  * id, name, current\_stock, unit (ml, pcs).  
* **service\_consumables\_bom** (Bill of Materials):  
  * Связывает service\_id и inventory\_item\_id.  
  * Поле quantity: сколько списывать за 1 процедуру.  
  * *Пример:* Услуга "УЗИ" списывает "Гель для УЗИ" (20 мл) и "Салфетка" (2 шт).

### **3.4. Расписание и Логистика (The Core)**

* **appointments**:  
  * id  
  * patient\_id (FK)  
  * staff\_id (FK)  
  * room\_id (FK)  
  * service\_id (FK)  
  * start\_time / end\_time (Timestamp).  
  * status (Enum: Planned, Confirmed, Completed, Cancelled, NoShow).  
  * **session\_sequence** (Int): Номер сеанса в курсе (1, 2,... 10).  
  * **funding\_source\_id** (FK): Кто платит за ЭТОТ конкретный сеанс.

### **3.5. Финансы (Смешанная оплата)**

* **funding\_sources**:  
  * id, name, type (Grant, Private, Insurance).  
* **patient\_balances**:  
  * patient\_id, funding\_source\_id.  
  * sessions\_limit (Int): Сколько сеансов оплатил фонд.  
  * sessions\_used (Int): Счетчик.  
  * **Logic:** При создании записи в appointments система проверяет, есть ли свободные слоты в гранте. Если sessions\_used \< sessions\_limit, то funding\_source ставится "Грант". Если лимит исчерпан — "Частная оплата".

## ---

**4\. Автоматизация: Роль Python-агента**

### **4.1. Алгоритм авто-расписания**

Это самая сложная часть. Алгоритм должен решить задачу "Укладки рюкзака" (Knapsack problem) в контексте времени.

* **Библиотека:** Google OR-Tools (CP-SAT Solver).  
* **Входные данные:** Список пациентов, требуемые процедуры, доступность врачей/залов.  
* **Ограничения (Constraints):**  
  1. Не пересекать время врача.  
  2. Не пересекать время зала.  
  3. Не пересекать время пациента.  
  4. Групповые занятия: Группировать пациентов с одинаковой услугой в один слот (до room.capacity).  
  5. Последовательность: Сеанс N+1 строго после сеанса N.

### **4.2. Форс-мажоры (Rescheduling Logic)**

Когда врач заболевает, кнопка "Форс-мажор" в NocoDB отправляет ID врача и дату в Python.

* **Действие:**  
  1. Python находит все встречи врача на этот день.  
  2. Меняет статус на Cancelled\_ForceMajeure.  
  3. Ищет ближайшее свободное окно в будущем.  
  4. **Сдвиг (Shift):** Переносит этот сеанс и *сдвигает все последующие сеансы* этого пациента на \+N дней, чтобы сохранить ритм лечения.

### **4.3. Склад и Списание**

Каждую ночь (или по событию) Python-скрипт сканирует таблицу appointments со статусом Completed.

* Для каждой услуги ищет спецификацию в service\_consumables\_bom.  
* Вычитает нужное количество из inventory\_items.  
* Если остаток \< минимума \-\> отправляет уведомление (Email/Telegram) администратору.
